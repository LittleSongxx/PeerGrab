# 2026-09-25 当前版本隔离栈压测工具冒烟

> 归档说明：本文保留实验发生时的日期、环境、结果与局限；代码、容器及配置标识已按 PeerGrab 当前命名整理。旧命令只说明当时的测试口径，复测请使用独立环境和当前运行说明。

本轮只验证工具与业务链路能在**独立 Compose 项目**中工作，不是容量测试。项目名 `peergrab-bench-smoke`，与演示栈使用不同的 MySQL/Redis/MQ 卷、端口和随机生成的口令；测试后整个项目及其数据卷已删除。API 与发压端仍在同一机器。下表的短时负载发生在本轮发布幂等补丁之前；该补丁随后通过全量集成测试与演示栈 HTTP 冒烟。

| 场景 | 输入 | 观察结果 |
| --- | --- | --- |
| S1 JWT 身份尖峰 | 8 个不同跑腿抢 1 个名额；另先用 30 个独立身份预热 | 成功 1、冲突 7、系统错误 0；P99 30ms。`run_id=20260925-223438`。`verify_run.sql` 校验 31 个任务零超卖、状态自洽、借贷平衡。 |
| S2-OPEN 列表读取 | 20 RPS，预热 1s、采样 3s | offered/completed/成功均 60，本地拒载 0、错误 0，P99 12.023ms。`run_id=20260925-223500`。 |
| S2-OPEN 列表读取 | 50 RPS，预热 1s、采样 3s | offered/completed/成功均 150，本地拒载 0、错误 0，P99 8.659ms。`run_id=20260925-223504`。 |

全新 Broker 命名卷初始归 root，RocketMQ 镜像中的 uid 3000 无法写入；此次冒烟发现后新增 `rmq-store-init`，先调整卷权限再启动 Broker。修复后 Broker 健康，MQ Topic 初始化和 API/Worker 启动成功；随后在另一个全新卷上用 `docker compose up -d --wait rmqbroker` 独立验证初始化依赖自动运行、Broker 健康。演示栈的旧卷已另行迁移并完成 HTTP 全生命周期及资金三层对账。

最终源码在全新隔离 MySQL/Redis 上执行 `mvn -Dpeergrab.it=true test`，141 项测试全部通过；本地 Docker 演示栈的 HTTP 冒烟又验证了同一发布键重放返回原任务且只扣款一次，以及发布→结算、取消退款、争议仲裁和 MQ 通知。资金 L1 借贷平衡、L2 系统户快照、L3 托管闭环及结算幂等/金额守恒均通过。

采样只有 3 秒，流量很小，未覆盖混合读写、长时间稳定性、CPU/GC/锁等待与故障窗口。这些数字不能用于判断最优并发或容量；正式容量实验按 [性能压测与架构决策方案](../../../docs/性能压测与架构决策方案.md) 执行。
