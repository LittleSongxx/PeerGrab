# PeerGrab 阿里云 ECS 8 核性能实测 · 2026-09-27

本轮在生产站点停机后，用独立压测栈复测任务广场列表、资金结算和抢单正确性。以下数字属于 **PeerGrab 的 8 核 ECS 实测**，与[原版项目历史评测](../original-project/README.md)分开归档；各场景也不能合成一个“全站 QPS”。

## 环境与口径

| 项目 | 本轮条件 |
| --- | --- |
| ECS | 阿里云香港，8 vCPU、标称 16 GB 内存（Linux 可见 14.97 GiB）；公网带宽由用户确认升级至 100 Mbps |
| 服务 | 生产容器停机；独立 Compose 项目及独立数据库、Redis、RocketMQ 和卷；app、worker 与上轮 4 核测试使用相同镜像摘要，测试容器无 CPU / 内存硬配额 |
| S2 数据和路径 | 10,000 条 `PUBLISHED` 任务；认证读取首屏 20 条，经 HTTPS → Host Nginx → 前端 Nginx → app，Host Nginx 上游 `keepalive 32` |
| S2 发压 | 独立工作站运行 Vegeta，固定到达率、HTTP/1.1、5 秒超时；各档先预热 20 秒，再采样 60 或 180 秒；发压端不占用 ECS CPU |
| S4 发压 | ECS 本机 Maven 客户端；独立任务事先发布和履约，只计并发结算阶段的数据库持久化结算 TPS；同任务重复结算、取消退款及仲裁退款另做正确性检查 |

S2 表中的 **目标请求**是 `offered QPS × 采样秒数`，**实际记录**是 Vegeta 真正发出并记录的请求数；两者不同须分别看。`HTTP 200` 是成功响应，`无响应`是超时或连接错误，不能写成应用返回 5xx。P99 对全部实际请求计时。资源指标取对应采样窗口内的 ECS 监控中位数。

## S2：完整代理路径的固定到达率

| 目标 QPS / 采样 | 目标请求 | 实际记录 | HTTP 200 | 无响应 | P99 | ECS CPU 中位 | 出网中位 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 450 / 60 秒 | 27,000 | 27,000 | 27,000 | 0 | 111.7 ms | 27.7% | 18.7 Mbps |
| 700 / 60 秒 | 42,000 | 42,000 | 42,000 | 0 | 140.5 ms | 40.4% | 29.1 Mbps |
| 900 / 60 秒 | 54,000 | 54,000 | 53,999 | 1 | 213.3 ms | 55.1% | 37.5 Mbps |
| 900 / 60 秒，复测 | 54,000 | 54,000 | 53,988 | 12 | 246.7 ms | 55.4% | 37.4 Mbps |
| 1,200 / 60 秒 | 72,000 | 72,000 | 71,997 | 3 | 321.2 ms | 75.4% | 50.2 Mbps |
| 1,350 / 60 秒 | 81,000 | 81,000 | 80,986 | 14 | 459.3 ms | 87.3% | 57.0 Mbps |
| 1,500 / 60 秒 | 90,000 | **88,689** | 88,689 | 0 | 3,134.8 ms | 99.3% | 61.8 Mbps |

1,500 QPS 档的发压器实际平均发出约 **1,478.2 QPS**，比目标少 **1,311 个请求**；88,689 个已发请求全部得到 HTTP 200，但长尾延迟超过 3 秒且整机 CPU 接近满载。因此它**不是**“1,500 QPS 零错误容量”。1,400 QPS 档的预热已经出现 1 次无响应，按脚本规则没有进入正式采样。900、1,200 和 1,350 QPS 档均发足目标请求，但已有无响应；100 Mbps 带宽未打满，而 1,350–1,500 档 CPU 与尾延迟明显上升，计算与排队是高档位的重要限制。较低档的少量无响应也不能仅凭整机 CPU 归因为计算瓶颈。

为检验持续性，又运行独立的 180 秒档：

| 目标 QPS | 目标请求 | 实际记录 | HTTP 200 | 无响应 | P99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 450 | 81,000 | 81,000 | 81,000 | 0 | 48.8 ms |
| 600 | 108,000 | 108,001 | 108,001 | 0 | 50.8 ms |
| 650 | 117,000 | 117,000 | 117,000 | 0 | 121.0 ms |
| 700 | 126,000 | 126,000 | 125,998 | 2 | 63.5 ms |
| 800 | 144,000 | 144,000 | 143,998 | 2 | 74.8 ms |

600 QPS 档 Vegeta 比理论目标多记录 1 个请求，表中保留原始数。**650 QPS 是本轮已验证的最高 180 秒零错误档位**；700 和 800 QPS 的同等时长档位均出现 2 次无响应。这是单接口、单台 ECS、三分钟窗口的观察结果，不代表全天候容量。60 秒档高负载下的完成吞吐也不能替代“全部目标请求发足且长期零错误”的判据。

## S4：资金结算与共享钱包竞争

每档先为独立任务完成发布、抢单和履约，再同时发起结算。下表 TPS 为**数据库中独立任务最终 `SETTLED` 数 ÷ 并发结算阶段耗时**，不包含预备、重复结算或退款阶段；P99 为结算请求延迟。

| 独立任务 / 客户端线程 | 持久化结算 TPS | 结算 P99 | 系统错误 |
| ---: | ---: | ---: | ---: |
| 20 / 4 | 19.83 | 431.4 ms | 0 |
| 50 / 8 | 34.31 | 333.2 ms | 0 |
| 100 / 16 | 46.49 | 419.0 ms | 0 |
| 200 / 32 | 57.44 | 732.0 ms | 0 |

从 16 增至 32 线程，持久化 TPS 增加约 24%，P99 增加约 75%，显示边际收益下降。S4 与随后的 S1 整个窗口累计增加 386 次 InnoDB 行锁等待、87.105 秒等待时间；这一合计**不能全部归给 S4**。四档 `bench_run` 与 SQL 校验均通过，结算、幂等、两类退款、资金借贷差、系统户快照及钱包总额均正确。S4 使用 ECS 本机客户端，结果包含发压进程对整机资源的占用。

同轮 S1 抢单在 16、64、128 人争夺同一名额时，三个档位均恰好 1 人成功、超卖 0、系统错误 0，P99 分别为 64、182、295 ms。它是有限时长的竞争尖峰，不能解释为稳态 QPS。

## 与 4 核 ECS 的同口径观察

只对照[上一轮 4 核报告](report-ecs-max-20260926.md)中请求、路径、持续时间与客户端模型一致的档位；两轮均为单次采样，以下变化不是可保证的扩容倍率。

| 指标 | 4 核 ECS | 8 核 ECS |
| --- | ---: | ---: |
| S2 完整路径，450 QPS × 180 秒 | 81,000 / 81,000 HTTP 200；P99 169.4 ms | 81,000 / 81,000 HTTP 200；P99 48.8 ms |
| S4，20 任务 / 4 线程 TPS | 15.24 | 19.83 |
| S4，50 任务 / 8 线程 TPS | 21.26 | 34.31 |
| S4，100 任务 / 16 线程 TPS | 22.32 | 46.49 |

两轮公网带宽分别为 50 和 100 Mbps；并发高档的差异同时受网络条件和测试时状态影响。S4 使用共享演示钱包，其 TPS 也不是所有真实用户独立钱包业务的统一上限。

## 证据与恢复

原始 Vegeta 聚合 JSON、逐两秒 ECS 与容器资源记录、S4/S1 `bench_run` 和 SQL 核验、环境镜像摘要保存在 Git 忽略的 `bench/runs/ecs-8cpu-20260927-evidence.tar.gz`；公开的[脱敏证据清单](ecs-8cpu-evidence.json)列出各轮结果与文件。原始包 SHA-256：`9615e0fb26fa058c3bc174755df93a2f1a92bdff22961c8ccaf7423a59e859d2`；本地与 ECS 私有副本校验一致。S2 与 S4 的工具源码提交分别为 `9f6adaee45c4b5319ca430f6f29588837b59abdf`、`782a3a7522045c99c9ea011fca4a247a6d784e21`，app 和 worker 镜像摘要与上一轮相同。

压测后，独立项目和卷、临时公网路由均已删除，生产的 7 个容器恢复运行。`https://www.peergrab.cn/api/health` 返回 HTTP 200，根域重定向到 `www`。生产库与停站前一致：任务 1、托管单 1、抢单记录 0、钱包账户 5、流水 4、钱包总额 110,000 分、借贷差 0；RocketMQ 的确认超时、自动结算、资金事件和缓存驱逐四个消费组各自 `Diff Total=0 / Inflight Total=0`。
