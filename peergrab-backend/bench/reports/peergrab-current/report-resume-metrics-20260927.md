# PeerGrab 简历指标专项复测 · 2026-09-27

本轮在维护窗口停掉线上生产栈，以同一版本应用镜像启动**独立压测栈**，完成完整公网入口读负载、同单抢单尖峰和持久化资金结算复测；结束后恢复生产栈。以下数字只适用于注明的接口、路径、数据规模和持续时间。它们是校招／实习简历可核验的项目证据，**不是全站长期容量或线上真实用户流量**。

## 环境与统计口径

| 项目 | 本轮条件 |
| --- | --- |
| 时间与机器 | 2026-09-27；阿里云香港 ECS，8 vCPU、约 14.97 GiB 内存、100 Mbps 公网带宽。下表原始时间戳为 UTC，北京时间加 8 小时。 |
| 服务与隔离 | 生产容器停止后使用 `peergrab-bench-resume0927` 独立 Compose 项目；独立 MySQL 8.0.40、Redis 7.4、RocketMQ 5.3.1 与数据卷。应用、Worker、前端镜像与已部署版本摘要一致；压测栈数据不进入生产库。 |
| 应用配置 | Tomcat 最大线程 200；Hikari 最大连接 20；抢单启用 Sentinel 热点限流，阈值 500/s；容器无 CPU／内存硬配额。 |
| 列表数据 | 预置 10,000 条 `PUBLISHED` 任务，S2 请求 `GET /api/errands?campusId=1&status=PUBLISHED&size=20`，读取首屏 20 条。它是单接口只读负载，没有模拟真实混合读写或生产用户分布。 |
| 两种请求路径 | S2 由独立工作站经**真实 HTTPS/HTTP/1.1 → 宿主 Nginx 临时压测路由 → 隔离前端 Nginx → 隔离 API** 发压。S1／S4 则由 ECS 内的 Java HTTP 客户端直连隔离 API `127.0.0.1:38220`；其延迟**不含公网或 Nginx**。 |

S2 的 RPS 是客户端按固定到达率计划发出的请求数／采样秒数；成功数单列。P99 是客户端看到的端到端响应延迟。S4 的 TPS 严格取 `distinct.durableSettled / distinct.elapsedSeconds`，只计独立任务的数据库持久化结算，不把准备任务、重复结算或退款计入分子。S1 是一次性同单竞争，不能用 `2,000 / 尖峰耗时` 冒充稳态 QPS。

## S2：完整 HTTPS 路径的持续列表读负载

Vegeta 在独立工作站以固定 600 RPS 各发压 180 秒，共重复 3 轮；每轮前另有 20 秒预热。`offered`、`resultRecords` 与 HTTP 200 分别核对，避免客户端漏发被误算为服务端成功。采样开始时间为 UTC。

| 轮次与采样开始 | offered／结果记录／HTTP 200 | 传输失败／其他 HTTP | 实际发出率 | P50／P95／P99 |
| --- | ---: | ---: | ---: | ---: |
| 1 · 12:21:08 | 108,000／108,000／108,000 | 0／0 | 600.005 RPS | 38.333／83.963／183.205 ms |
| 2 · 12:25:21 | 108,000／108,000／108,000 | 0／0 | 600.007 RPS | 38.384／87.621／256.232 ms |
| 3 · 12:29:13 | 108,000／108,000／108,000 | 0／0 | 600.005 RPS | 37.706／48.765／93.025 ms |

因此能写“**完整 HTTPS 路径的任务列表接口在 600 RPS、每轮 3 分钟、3 轮共 324,000 请求中全部返回 HTTP 200，最差轮 P99 为 256.232 ms**”。它表明此负载下的可重复表现，不表明 600 RPS 是最大吞吐，也不代表所有接口达到相同延迟。第一轮资源样本约 2 秒一采，主机 CPU 中位数约 **36.6%**；同轮 Hikari `active` 峰值 9／20、`pending` 峰值 0、连接超时增量 0。资源数字只是该轮采样观察，不是服务器持续资源上限。

为探测失败边界，还单独执行了每档 60 秒的 450／600／750 RPS 阶梯及 650 RPS × 180 秒。450、600 两档均发足且无错误；750 档计划 45,000 次，有 **1 次传输超时**；650 档计划 117,000 次，记录 117,001 个结果，其中 116,978 个 HTTP 200、**23 次传输超时**。650 档结果记录比计划数多 1，按原始记录披露，不用其计算精确错误率。由此不能宣称 650 或 750 RPS 零错误，也不能把 600 RPS 写成“最大 QPS”。过载定位尚需区分客户端、HTTPS/Nginx、应用和数据库阶段。

## S1：2,000 人同抢 1 个名额

同机 Java HTTP 客户端以 2,000 个并发请求争抢每轮新建的 1 名额任务，3 轮各有 1 人成功。热键限流、名额已满与并发冲突是**预期业务结果**，不能写成“2,000 人都抢单成功”；`errors=0` 指工具记录的系统错误为 0。

| 轮次（北京时间） | 成功／超卖／系统错误 | 名额满／并发冲突／热点限流 | 请求 P99 | 数据库校验 |
| --- | ---: | ---: | ---: | --- |
| 20:42:35 | 1／0／0 | 1,837／4／158 | 3,142 ms | PASS |
| 20:43:41 | 1／0／0 | 1,828／4／167 | 2,954 ms | PASS |
| 20:44:17 | 1／0／0 | 1,793／2／204 | 2,771 ms | PASS |

每轮数据库 `verify_run.sql` 核对名额、抢中记录、任务状态与借贷平衡，结果为 PASS。这里最有价值的是**限流参与下的单名额正确性**：共 3 次独立 2,000 并发尖峰，每次恰好 1 人成功且无超卖；本轮 P99 为 2.77–3.14 秒，不能称为低延迟抢单，也不能用它推导稳定 QPS。

## S4：共享钱包下的持久化结算

同机客户端先准备不同任务，再按指定线程数执行结算；准备阶段不计入 TPS。两次完整低到高阶梯记录如下。每档还单独做同一任务 8 次重复结算（1 次成功、7 次业务拒绝）、取消和仲裁退款；SQL 核对借贷平衡、系统户快照、托管闭环、金额守恒和单名额无超卖。

| 独立任务／客户端线程 | 第 1 轮：持久化 TPS／P99 | 第 2 轮：持久化 TPS／P99 |
| ---: | ---: | ---: |
| 20／4 | 36.839／153.174 ms | 65.354／74.942 ms |
| 50／8 | 55.830／171.162 ms | 67.305／145.261 ms |
| 100／16 | 63.718／290.372 ms | 70.649／251.356 ms |
| **200／32** | **60.781／683.448 ms** | **60.269／727.402 ms** |

最高档两轮分别在 3.290／3.318 秒内完成 **200／200 个独立持久化结算**，系统错误 0、资金差额 0；重复结算和退款校验亦通过。由于所有测试任务复用演示发布者、跑腿者等少量钱包，这个结果**包含共享钱包行锁竞争**，也只是数秒批次 TPS，不证明“结算服务长期稳定 60 TPS”或不同真实钱包分布的容量。小样本档位虽有更高 TPS，不能用 20 个任务／0.3 秒的数值报系统峰值。行锁等待计数覆盖造数与核验，不能全归因于结算请求。

## 与已发布 S3／S5 证据的关系

[上一份上线后 ECS 复测报告](report-ecs-release-20260927.md)记录了 S3 缓存消融与 S5 到期流转；本轮**未重跑**这两项。S3 热缓存把 5,000 次详情读的数据库加载降为 0，但热轮吞吐 **661 RPS 低于无缓存的 680 RPS**，只能说减轻数据库读负载，不能说吞吐提升。S5 的 MQ 与扫描独占轮各完成 1,000／1,000，到期后持久化 P99 分别为 9.058／39.472 秒；每种机制仅一轮，且不是同机制 A/B 加速实验。上述指标不能与本轮 S2/S4 混成同一工作负载或宣称全面性能提升。
