# 当前镜像 ECS 六类场景性能与故障实测（2026-09-28）

本报告记录 **ECS 上当前应用镜像**的一次隔离压测窗口。它回答指定业务路径、数据规模和负载下的表现；**没有测出全站最大稳定 QPS，也没有完成长期 SLA 验证**。执行入口和资产保留规则见 [bench 运行手册](../../README.md) 与 [评测资产目录](../../ASSET_CATALOG.md)。图示中的旧版同机 6000+ QPS 与本报告的公网 HTTPS 数字不是同一负载或机器，不能拼接成一条容量曲线。

## 环境、模型与判定口径

- 目标是一台 8 vCPU、100 Mbps 的阿里云 ECS，应用和中间件同机部署。压测时停止 `peergrab-prod`；每个场景使用独立 `peergrab-bench-spectrum-*` Compose 项目、新 MySQL/Redis/RocketMQ 卷，预检容器、网络、端口和数据库标记。同一时刻只运行一个隔离项目。应用镜像 ID 为 `sha256:387c3ec4139df1053a2505f42d5214284935ab8c98573c77df7cffb93725a0c2`，Worker 镜像 ID 为 `sha256:40df63e12308802fd50d3da4b4142b5ae56eb173796b946e5b0a0beeb7960177`，对应已上线的 `5ace500` 业务改动；`e85f9b4`、`d5bbee8`、`f08c77f` 仅改变压测客户端、故障探针和文档。MySQL 8.0.40、Redis 7.4、RocketMQ 5.3.1；S2 等普通轮的 Tomcat 最大线程 200、Hikari 最大连接 20。
- S2 使用**异机 Vegeta 固定到达率**、真实公网 HTTPS、宿主 Nginx → 隔离前端 Nginx → API，验证证书，HTTP/1.1；S1/S3/S4 的 Java HTTP 客户端及 S6 的 Python 故障探针走 ECS 回环地址，S5 MQ 探针在隔离网络内运行，因而这些场景不含公网和两层 Nginx 的开销。S3/S4 是固定工作线程的有限批次，S1 是一次开闸尖峰，S5 是统一时刻到期，S6 是故障冒烟；这些结果不能称为持续 QPS。固定到达率与固定并发的差异见 [k6 官方说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)；Vegeta 官方也要求区分目标与实际发送速率（[说明](https://github.com/tsenart/vegeta#-rate)）。
- `P99` 是对应客户端或状态日志定义的分位数。表内“错误”区分 HTTP 非 2xx、传输超时及预期业务拒绝；不能把 `SLOT_FULL` 等业务结果记作系统错误，也不能把传输超时从成功响应 P99 中隐去。每轮保留客户端结果、服务器指标快照、数据库及资金校验；原始证据归档见文末。

## S2：广场首屏游标列表，经完整公网 HTTPS

工作集为同校区 10,000 条 `PUBLISHED` 任务；请求为 `GET /api/errands?campusId=1&cursor=&size=20`，这次确实进入广场首屏游标分支。固定同一个首页与一个压测身份，因此**不能推广到后续游标页、混合列表、其他用户或全站容量**。每档单独预热 20 秒，阶梯采样 60 秒；随后在同一隔离栈上做三轮 600 RPS × 180 秒。下表的 P99 为客户端全请求耗时，计数分母为采样期计划发送且实际产出结果的请求。

| 档位与采样 | 发出／结果 | HTTP 200 | HTTP 其他 | 传输超时 | 客户端 P50／P95／P99 | 实际发出速率 |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| 450 RPS × 60 秒 | 27,000／27,000 | 27,000 | 0 | 0 | 34.128／40.533／64.889 ms | 450.024/s |
| 600 RPS × 60 秒 | 36,000／36,000 | 36,000 | 0 | 0 | 34.850／41.315／79.547 ms | 600.016/s |
| 650 RPS × 60 秒 | 39,000／39,000 | 39,000 | 0 | 0 | 33.995／44.142／139.304 ms | 650.018/s |
| 600 RPS × 180 秒，轮 1 | 108,000／108,000 | 108,000 | 0 | 0 | 34.300／41.536／46.919 ms | 600.005/s |
| 600 RPS × 180 秒，轮 2 | 108,000／108,000 | 108,000 | 0 | 0 | 34.186／42.778／52.332 ms | 600.008/s |
| 600 RPS × 180 秒，轮 3 | 108,000／108,000 | 107,996 | 0 | **4** | 33.856／41.537／47.839 ms | 600.007/s |

三轮长档合计 **324,000 次尝试、323,996 次 HTTP 200、4 次传输超时**；第三轮整体 P99 约 48 ms 不能替代超时数量这一尾部体验指标。按成功数／采样 180 秒计，该轮有效 HTTP 200 吞吐为 599.978/s。650 RPS 只持续 60 秒，不能宣称 650 RPS 长期稳定，也不能据此断定容量拐点。Vegeta 结果保留每秒**完成数**和累计分位数，但未保存每秒原始发出时间戳与单请求业务 JSON 校验；`max-body=0` 意味着响应体被读取但不保留。

S2 异机发压进程长档样本最大 RSS 62 MiB、文件描述符 439，CPU 中位约占单核 23%；三个 600 长档实际发出速率均接近 600/s，没有看到发压端明显漏发。ECS 的 2 秒资源采样完整覆盖长档前两轮采样窗口：宿主 CPU 中位 **33.7%／33.1%**，公网发送中位约 **23.1 Mbps**，I/O 等待中位 0.12%；第三轮只覆盖前 69 个采样点，**不能把该轮采样 CPU 当作完整窗口结论**。阶梯采样器在 650 RPS 前结束，因此 650 档没有完整资源曲线。临时脱敏 Nginx 计时日志共 496,167 条，全部 200，记录中的最大 `$request_time` 207 ms；其中还包含预热和探针，不能简单与六个采样档的请求数一一相减，也不能仅凭 HTTP 日志确定 4 次超时的 TCP/TLS 阶段。之前同路径定位已将稀有公网超时缩小到宿主 Nginx 完成 HTTP 请求处理之前；本轮仍需双端连接阶段证据才能定责。Nginx 时间变量定义见[官方文档](https://nginx.org/en/docs/http/ngx_http_log_module.html)。

## S1：同一名额 2,000 人瞬时抢单

两次均在全新隔离栈，以 2,000 个不同跑腿身份抢一个名额。`SpikeLoadClient` 用屏障同时放行虚拟线程，但发压器尚需调度及建立 HTTP 连接，故“放行”不等于 2,000 个请求在同一纳秒到达应用。客户端延迟为 `send` 到完成，另记放行到发出与完成的时差。

| 轮次 | 成功／满额／冲突／限流／系统错误 | `send`→完成 P50／P99 | 放行→`send` P99 | 放行→完成 P99 | 整批 |
| --- | --- | --- | ---: | ---: | ---: |
| A | 1／1,997／2／0／0 | 3,042／4,682 ms | 1,396 ms | 5,637 ms | 5.653 s |
| B | 1／1,998／1／0／0 | 3,147／5,081 ms | 1,267 ms | 5,847 ms | 5.863 s |

应用结果和独立 SQL 均核对“恰好一个抢中、名额无超卖、状态自洽、借贷平衡”通过。`2,000÷整批秒数` 只是该尖峰的完成速率参考，**不是稳定抢单 TPS**。`SLOT_FULL` 是预期业务拒绝，但其 3–5 秒尾延迟是真实请求体验；本轮未观测到限流，并不证明限流机制失效。与阶段性优化单轮相比到达形状、客户端调度和热度都可能不同，不宣称代码性能回退或提升。

## S3：详情缓存关／开、热 Key、9:1 读写

缓存关与开分别用新隔离项目和 10,000 条任务；每个项目执行 3 个连续的 5,000 次详情读有限批次，50 工作线程。第 1 次是“该栈首次读取”，第 2/3 次共享 JVM、连接和缓存热度，**不是三份完全独立的冷启动样本**。

| 配置 | 三次 5,000 读的完成 RPS | 三次 P99 | 三次详情回源 | 三次详情命中 |
| --- | --- | --- | --- | --- |
| A：关闭详情缓存 | 508／648／963 | 242／165／129 ms | 5,000／5,000／5,000 | 0／0／0 |
| B：开启详情缓存 | 510／751／1,006 | 357／133／109 ms | 101／0／0 | 4,899／5,000／5,000 |

三批共 15,000 次请求对应的 MySQL `Com_select` 增量：A 为 **30,145**，B 为 **15,239**，少 14,906 次（约 49.5%）；这比仅报“详情回源从 5,000 到 0”更接近数据库整体读负担，但仍是整个窗口的实例级计数，含鉴权和少量后台查询，不是逐请求 SQL 精确归因。两组吞吐均随批次明显上升，不能只拿末轮 1,006 对 963 宣称稳定提升；首次缓存开启 P99 357 ms 高于关闭的 242 ms，需把冷态代价一并说清。额外单次 90% 请求打同一详情 Key：5,000/5,000 成功、回源 0、P99 127 ms；没有单分片／多分片对照，不能证明“热点分片优化”。

读写混合只在缓存开启的新栈上运行一次：**500 次发布 + 4,500 次对新发布任务的详情读**，50 工作线程，5,000/5,000 成功，有限批次完成 329/s、混合 P99 945 ms，详情回源 576、命中 3,924。每个工作线程每发布一单随后读该新单 9 次；抽取首个新单验证 `PUBLISHED`，取消后再读到 `CANCELLED`，缓存一致性抽样检查 `diffs=0`。该抽样**不代表全部 500 个新单在所有并发时刻都零陈旧**，混合 P99 也没有分开发布与读取，不能当作详情读 P99。`Com_select` 为 MySQL 累计状态计数，其定义见[官方文档](https://dev.mysql.com/doc/refman/8.0/en/server-status-variables.html)。

## S4：经 HTTP 的并发结算、重复结算与资金校验

两次全新栈各以 32 客户端工作线程准备并结算 200 个不同任务，再对同一任务发出 8 次结算尝试。准备工作不计入 TPS，结算 TPS 取**数据库持久成功的 200 单／该批次耗时**，因此是约 5 秒的共享钱包热点批次，而非长时间稳态容量。所有不同任务结算 200/200 成功；同单均恰好 1 次成功、7 次业务拒绝，系统错误 0。

| 轮次 | 200 单持久结算 TPS | 不同任务尝试 P50／P95／P99 | 同单重复成功／拒绝 | 资金差额 |
| --- | ---: | --- | --- | ---: |
| A | 39.52 | 707／1,311／1,446 ms | 1／7 | 0 |
| B | 36.09 | 759／1,365／1,483 ms | 1／7 | 0 |

每轮账本借贷、系统户快照、托管闭环及钱包总额均通过；数据库 `Innodb_row_lock_waits` 从 0 增至 **206**，`Innodb_row_lock_time` 增 **82,611／89,703 ms**。它是**窗口内所有事务累计等待时间**，包含准备阶段和同单重复结算，不能除以 200 当作单请求延迟；但与共享发布者、跑腿者、系统钱包和信用行的行锁竞争一致。MySQL 对该变量的定义为获取 InnoDB 行锁所花的总毫秒数（[官方文档](https://dev.mysql.com/doc/refman/8.0/en/server-status-variables.html)）。本轮没有分散钱包用户的同条件对照、长时稳定负载或逐账户金额全量审计，不能给出无热点结算容量。

## S5：1,000 单同刻到期，MQ 主通道和扫描兜底分开

两轮均预置 1,000 条 `LOCKED` 任务，设未来同一个截止时刻，确认宽限 5 秒、Worker 扫描间隔 5 秒；MQ 轮关闭扫描，兜底轮关闭 MQ，各自新栈。探针使用 `errand_status_log.created_at` 与预定截止时刻之差；该时间戳在事务内写入，**不是精确的事务提交或其他会话可见时刻**。[测量口径](../../S5_TIMELINE.md)。

| 路径 | 已处理／未处理／重复／提前／错误状态 | 到期→状态日志 P50／P95／P99／最大 | 排空特征 |
| --- | --- | --- | --- |
| MQ 定时消息 | 1,000／0／0／0／0 | 5.914／9.241／9.512／24.802 s | 999 条约 10 秒内完成，最后 1 条约 24.8 秒 |
| 扫描兜底 | 1,000／0／0／0／0 | 13.610／24.628／25.100／25.207 s | 约 25 秒全部排空，出现批次间停顿 |

MQ 结束时单次消费者快照 `Diff Total=0`、`Inflight Total=0`，只说明结束时无积压，不反映运行中峰值；`peakBusinessBacklog=1000` 是未流转任务数，不是 MQ 堆积。RocketMQ 官方明确提醒大量消息设为同一投递时刻可能造成投递延迟（[官方说明](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)）。两条路径各只测 1,000 条一次，不证明 10,000 条、长期吞吐或所有截止分布下的延迟。

## S6：单节点暂停故障与恢复冒烟

此项是在**隔离栈**用 `docker pause` 暂停一个 Redis 或 Broker 容器；它测的是给定 25–30 秒左右的单次故障和恢复，不是主从切换、高可用 SLA 或稳态故障容量。[探针及通过条件](../../S6_FAULT_SMOKE.md)。

- **Redis 暂停，正式有效轮**：暂停前／期间／恢复后均按固定 10 RPS 读取详情，分别计划并发出 **50／250／50** 次，全部 HTTP 与业务成功，无发压器漏发或本地拒发；客户端 P95 **14.440／2,013.163／9.002 ms**。暂停期间一笔真实抢单由数据库裁决，最终 `LOCKED`、名额 1/1、恰好一条 `GRABBED`，资金不变量通过。首次执行同样 250 次请求虽成功，却碰到探针硬看门狗截止与解冻竞争，被标为**无效失败轮**，不作为故障容量数字；修正看门狗余量后重建新栈取得上述正式结果。
- **MQ 暂停，生产默认配置的失败轮**：客户端对结算的 **8 秒超时**触发传输失败；应用侧同一结算请求稍后记录 HTTP 200、耗时 **8.204 s**，任务已 `SETTLED`、托管单 `RELEASED`、三条结算流水正确。解冻后的证据中 outbox 为 `SENT`、两条通知到达，资金校验全过。客户端无法知道已提交而可能重试，这是比吞吐数字更重要的行为风险；本轮必须标为**故障体验失败**，不能用“资金最终正确”掩盖超时。
- **MQ 暂停，隔离配置对照**：在新栈**只关闭延迟双删**（`peergrab.cache.double-delete-enabled=false`）后重做同一单笔流程，Broker 继续暂停约 27 秒，结算应用 HTTP 200 耗时 **94.856 ms**；恢复后 outbox、通知和资金校验通过。这支持“提交后同步发送延迟双删消息参与默认轮 HTTP 阻塞”的判断，但没有单独的发送调用耗时或线程栈，不能把全部 8.204 秒精确归因于该调用。此设置**仅用于隔离对照，未部署生产**；关闭双删还涉及缓存一致性取舍，不能当作已完成修复。

原始客户端归档在 Git 忽略目录 `bench/runs/spectrum-20260928/spectrum-client-evidence.tar.gz`，SHA-256 `674ed6f56ee8f904b5d88af26e789a6255cd3be8247f99295d5eb662f17c2d98`；服务器归档为 `bench/runs/spectrum-20260928/spectrum-server-evidence.tar.gz`，SHA-256 `643733d076388732a9ecdcb618eff69449de6e6f4ff9c996330f26602dd1b9db`。服务器另存于 ECS 仓库外私有维护目录。归档含脱敏时序、Prometheus、MySQL/Redis 快照、SQL 核验和恢复记录，故不公开提交。可复现入口是 [S2 Vegeta 包装器](../../scripts/run_remote_s2_vegeta.py)、[S3 客户端](../../../peergrab-bench/src/main/java/com/peergrab/bench/CacheLoadClient.java)、[S1 客户端](../../../peergrab-bench/src/main/java/com/peergrab/bench/SpikeLoadClient.java)、[S4 客户端](../../../peergrab-bench/src/main/java/com/peergrab/bench/FundsHttpLoadClient.java)、[S5 探针](../../../peergrab-bench/src/main/java/com/peergrab/bench/S5TimelineProbe.java)及 [S6 故障探针](../../scripts/run_s6_fault_smoke.py)。

本轮最明确的性能／可靠性结论是：**当前游标首屏在 600 offered RPS 三次 180 秒公网测试中维持约 600/s HTTP 200，但仍有 4 次公开链路传输超时；热点抢单与共享钱包结算的尾延迟高；同刻到期在本轮规模下 MQ 和扫描最终都排空；Redis 暂停能回源但约 2 秒 P95；默认 MQ 故障时已提交结算可能晚于客户端超时返回。**后续若要声称全站稳定容量或简历级 SLA，仍需多游标页／多用户读写混合、多轮分散钱包结算、长期稳态及故障窗口连续负载，并保留逐秒实际发出、完成和客户端／服务端资源曲线。
