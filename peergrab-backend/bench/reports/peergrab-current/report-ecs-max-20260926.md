# PeerGrab 阿里云 ECS 独立栈性能实测 · 2026-09-26—27

本轮以 **S2 任务广场首屏列表**定位固定到达率拐点，并分别记录 S1 抢单、S3 缓存、S4 结算和 S5 自然到期；各场景不能合成一个全站容量数字。测试期间公开演示栈已在私有备份后停机；S2/S1/S4 使用 `peergrab-bench-max0926` 隔离项目，S3 和 S5 的各个对照使用全新项目、数据库与卷，均不写生产数据。

## 环境与口径

| 项目 | 本轮实际条件 |
| --- | --- |
| ECS | 阿里云香港，4 vCPU、约 15 GiB 可见内存、Ubuntu 24.04；公网带宽在本轮升至 50 Mbps |
| 应用 | 与生产同一 app/worker 镜像；测试容器**无 CPU 和内存硬配额**，生产容器停机 |
| 数据 | 隔离库固定 10,000 条 `PUBLISHED` 任务；认证 GET `/api/errands?campusId=1&status=PUBLISHED&size=20`，响应体约 4,701 字节 |
| 发压 | 独立工作站经 TLS 到 ECS 上限 IP 的临时白名单路由；路由前后与隔离数据库任务 ID 交叉校验，工作站并不占用 ECS CPU |
| 统计 | 固定到达率 `offered/s`；`HTTP 200/s` 为成功 HTTP 响应，`status=0` 表示没有取得 HTTP 响应；P99 是全部尝试的请求延迟。每档预热、采样时长见下表 |

早期 SSH 转发试验的 `sshd` 在 650 RPS 时消耗约 0.8 个 ECS CPU 核，不能代表公网路径容量，因此以下极限表采用直连 HTTPS。客户端 Python 调度错过数仍会单列；正式拐点复核采用 [Vegeta 固定速率发压器](https://github.com/tsenart/vegeta) v12.13.0。

## Nginx 上游连接复用 A/B/A

这组请求经 Host Nginx **直达隔离 app**；只改变临时路由的上游连接复用，保持相同数据、app 与 625 offered QPS，每轮采样 60 秒。B 设置 `keepalive 128` 并清空上游 `Connection` 头；A 使用原有短连接设置。[Nginx 官方文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)描述了该配置。三轮的服务端 HTTP 错误均为零。

| 顺序 | 上游连接 | 采样 HTTP 200/s | 客户端错过发送 | P95 | P99 | ECS CPU 中位值 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A1 | 短连接 | 624.5 | 5 | 236.5 ms | 560.0 ms | 约 78% |
| B | `keepalive 128` | 622.8 | 54 | 85.3 ms | 166.8 ms | 约 64% |
| A2 | 短连接 | 623.0 | 98 | 344.9 ms | 651.2 ms | 约 84% |

B 的 P99 比两次 A 低约 70–74%；A2 回退后再次上升。三轮各有少量 Python 发压端调度错过，不能拿表中的 1–2 QPS 差值解释服务端吞吐提升。这个临时路径绕过了正式部署的前端 Nginx，`keepalive 128` 的收益也不能直接外推到拟用于生产 Host Nginx 的 `keepalive 32`。

## S2 固定到达率与性能拐点

以下采用临时路由 `keepalive 128`、应用默认 Hikari 20 / Tomcat 200、独立工作站 Vegeta HTTP/1.1 发压；app 与 MySQL 无 Docker CPU 配额。`status=0` 是无 HTTP 响应，**不是应用返回 HTTP 0 或 5xx**。

| offered/s | 预热 / 采样 | 采样结果 | P99 | ECS CPU 中位值 | 判读 |
| ---: | --- | --- | ---: | ---: | --- |
| 700 | 10 / 30 秒 | 21,000 / 21,000 HTTP 200 | 220.6 ms | — | 短档通过 |
| 700 | 20 / 60 秒 | 42,000 / 42,000 HTTP 200 | 400.6 ms | 约 75% | 长档通过 |
| 720 | 20 / 60 秒 | 43,192 HTTP 200、8 无响应 | 560.3 ms | — | 边缘，首次失稳 |
| 720 | 20 / 60 秒 | 43,200 / 43,200 HTTP 200 | 434.8 ms | 约 77% | 重跑通过 |
| 750 | 20 / 60 秒 | 44,980 HTTP 200、20 无响应 | 1,991.2 ms | 约 99% | 持续排队，未通过 |
| 800 | 10 / 30 秒 | 23,994 HTTP 200、6 无响应 | 557.2 ms | 约 87% | 短档未通过 |

在本轮**单接口、60 秒负载**下，700 offered QPS 已重复取得零错误，720 QPS 两轮结果有波动，750 QPS 尾延迟和无响应明显上升。可复现的实用上限目前以 700 QPS 计，拐点位于约 700–750 QPS。750 QPS 失稳轮的 ECS CPU 中位值约 99%，公网发送约 32 Mbps、I/O 等待约 0%；结合 50 Mbps 的带宽上限，主要限制是 4 vCPU 的整机计算与请求排队，带宽尚未打满。不能把 30 秒的最高 HTTP 200/s 当成长期稳定容量。

## Hikari 与 Tomcat 消融

只重建隔离 app，固定同一数据库、10,000 条列表种子、Worker 与卷；每次重建后先按 300→500→600 QPS 逐级预热，再比较 650 offered QPS 的 60 秒采样。直接在新 JVM 刚健康时跳到 650 QPS 的轮次曾出现大量 5 秒超时，即使后来恢复默认参数也能复现；这些冷态异常轮不用于选型。

| app 配置 | 650 QPS 正式采样 | P99 | 判读 |
| --- | --- | ---: | --- |
| Hikari 8 / Tomcat 200 | 39,000 / 39,000 HTTP 200 | 433.5 ms | 一轮热态通过 |
| Hikari 20 / Tomcat 200 | 39,000 / 39,000 HTTP 200 | 566.3 ms | 一轮热态通过；另一个 30 秒档 P99 为 226.3 ms |
| Hikari 20 / Tomcat 64 | 39,000 / 39,000 HTTP 200 | 346.0 ms | 一轮热态通过 |

两种缩小配置均没有带来可重复的吞吐上限提升；尾延迟在热态轮之间仍有明显波动，默认参数回退轮又在预热阶段出现少量超时，无法据一轮 P99 排出可靠优先级。**应用参数保持 Hikari 20 / Tomcat 200**，后续若要更改，应加入连接池等待数和 Tomcat busy 线程观测并做多轮交错复测。

## 完整公开路径：Host Nginx → 前端 Nginx → App

在相同隔离栈中启动生产前端镜像，只绑定 ECS 回环 `127.0.0.1:38082`；临时公网白名单路由改为经过该前端，Host Nginx 使用 `keepalive 32`。保留同一 app、数据库与 10,000 条任务，外部 Vegeta 每档预热 20 秒、采样 60 秒。

| offered/s | HTTP 200 / 尝试 | P95 | P99 | ECS CPU 中位值 |
| ---: | ---: | ---: | ---: | ---: |
| 400 | 24,000 / 24,000 | — | 151.1 ms | 约 57% |
| 400，持续 180 秒 | 72,000 / 72,000 | 52.5 ms | 71.3 ms | 约 55% |
| 450，持续 180 秒 | 81,000 / 81,000 | 62.4 ms | 169.4 ms | 约 61% |
| 500 | 30,000 / 30,000 | 97.0 ms | 187.8 ms | 约 70% |
| 500，持续 180 秒 | 89,994 / 90,000；6 无响应 | 159.4 ms | 627.9 ms | — |
| 525 | 31,501 / 31,501 | 208.1 ms | 331.1 ms | — |
| 550 | 33,000 / 33,000 | 565.5 ms | 949.4 ms | 约 80% |
| 575 | 34,499 / 34,500；1 无响应 | — | 1,044.5 ms | — |
| 650 | 38,589 / 39,000；411 无响应 | 3,949.8 ms | 4,975.7 ms | 约 99.5% |

前端代理在 400 QPS 时约用单核 22% 的 CPU；完整路径 650 QPS 档出网中位约 29 Mbps、I/O 等待约 0。**450 QPS 已在 180 秒内零错误；500 QPS 在 60 秒内零错误且 P99 低于 200 ms，但 180 秒档出现 6 次 5 秒超时，不能称为同等时长的零错误容量。** 525 QPS 的 P99 升至约 331 ms，550 QPS 逼近 1 秒，575 QPS 出现无响应。尾延迟拐点约在 525–550 QPS；以本轮验证口径，450 QPS 是经 3 分钟复核的保守持续档位。

### Host Nginx 连接复用的完整路径对照

保持隔离前端、app、数据库和 500 offered QPS 不变，只切换 Host Nginx 到前端的上游连接设置，按 A/B/A 各采样 60 秒。三轮均 30,000/30,000 HTTP 200。

| 顺序 | Host Nginx → 前端 | P95 | P99 | ECS CPU 中位值 |
| --- | --- | ---: | ---: | ---: |
| A1 | `keepalive 32` | 97.0 ms | 187.8 ms | 约 70% |
| B | 短连接 | 576.8 ms | 1,139.1 ms | 约 82% |
| A2 | 恢复 `keepalive 32` | 103.4 ms | 176.9 ms | 约 67% |

恢复连接复用后 P99 和 CPU 均回落。这一对照包含正式部署中的双层代理，支持将 Host Nginx 的 `keepalive 32` 用于生产；WebSocket 仍保留 `Connection: upgrade`。

## S4 结算与 S1 抢单

完成 S2 后，在同一隔离栈经回环 API 运行写入场景，**先 S4 后 S1**。S4 客户端独立创建并履约任务，再并发结算；每档还执行同任务重复结算、取消退款和仲裁退款。客户端、`bench_run` 与 SQL 验证全部 PASS；资金借贷差、系统户快照差和钱包总额差均为 0，两类退款和幂等结算数量正确。

| S4 独立任务 / 线程 | 持久化结算 TPS | 结算请求 P99 | 系统错误 |
| ---: | ---: | ---: | ---: |
| 20 / 4 | 15.24 | 407.0 ms | 0 |
| 50 / 8 | 21.26 | 530.1 ms | 0 |
| 100 / 16 | 22.32 | 874.4 ms | 0 |

8→16 线程仅增加约 5% 的持久化 TPS，P99 却增加约 65%。该场景共用发布者、跑腿者及系统托管/佣金钱包行；本轮所有 S4 预热与正式任务累计出现 215 次 InnoDB 行锁等待、约 53.9 秒等待时间。因此 S4 的主要扩展限制更像共享钱包锁竞争，不能用 S2 的 CPU 拐点代表结算容量。

| S1 同任务瞬时竞争 | 抢中 / 超卖 / 系统错误 | P99 |
| ---: | --- | ---: |
| 16 人 / 1 名额 | 1 / 0 / 0 | 130 ms |
| 64 人 / 1 名额 | 1 / 0 / 0 | 343 ms |
| 128 人 / 1 名额 | 1 / 0 / 0 | 804 ms |

S1 是有限时长的同一任务爆发，`并发数 ÷ 爆发耗时` 不属于稳态 QPS。六个正式档结束后，原有 10,000 条 S2 任务的完整行哈希仍为 `c5a1ac3cdf6e4cbcf324aa6207715451d2487f48472ded5b7bb41393fb98e00c`，全部保持 `PUBLISHED`；隔离库钱包总额仍为 110,000 分，流水借贷差为 0。两轮额外 S4 20/4 预热虽业务 PASS，但自动采集器因 MySQL 中文校验 SQL 的字符集问题停在正式记录前；修复为 `utf8mb4` 后，报告仅采用最后一轮完整校验的六档。

## S3 详情缓存开关

缓存关闭与开启各使用一套**新项目、新卷**，均造 100 条发布任务并重建 Bloom。客户端在每个项目连续执行两轮 50 并发 ×100 次详情读取；四轮均 5,000/5,000 成功、零失败。RPS 是有限请求批次的封闭循环完成速率，不能当成固定到达率的容量上限。

| 配置 | 冷态 RPS / P99 / 回源 / 命中 | 热态 RPS / P99 / 回源 / 命中 |
| --- | --- | --- |
| 详情缓存关闭 | 238 / 468 ms / 5,000 / 0 | 317 / 362 ms / 5,000 / 0 |
| 详情缓存开启，4 片 | 273 / 628 ms / 100 / 4,900 | 406 / 264 ms / 0 / 5,000 |

热态缓存开启相对关闭完成速率约高 28%、P99 约低 27%，回源从 5,000 次降至 0；冷态 P99 反而更高。此处只验证了缓存开关，未把 1/4 分片和读写混合场景混入这个对照。

## S5 自然到期：MQ 与兜底扫描

MQ 独占与扫描独占分别使用全新项目和卷；两组 Worker 的确认超时均为 5 秒。MQ 组关闭扫描，扫描组关闭 MQ；先插入未来到期的 `LOCKED` 任务，再从数据库记录的**到期时刻**起计算状态落盘延迟。四项正确性条件是未处理、重复处理、提前处理和错误状态均为 0。独立 2 秒 RocketMQ 定时消息探针通过，第一次 Broker 的实际投递比目标晚约 1.00 秒。

| 独占通道 | 任务数 | 完成 / 正确性 | P50 / P95 / P99 | 最后一条到期后落盘 | 平均 / 峰值落盘数每秒 |
| --- | ---: | --- | --- | ---: | ---: |
| MQ 定时消息 | 1,000 | 1,000 / 四项全 0 | 9.83 / 16.27 / 16.79 s | 16.96 s | 59.0 / 86 |
| MQ 定时消息 | 5,000 | 5,000 / 四项全 0 | 36.33 / 58.21 / 59.84 s | 60.20 s | 83.1 / 138 |
| 兜底扫描，5 秒间隔 | 1,000 | 1,000 / 四项全 0 | 25.21 / 45.77 / 46.66 s | 46.88 s | 21.3 / 47 |
| 兜底扫描，5 秒间隔 | 5,000 | 5,000 / 四项全 0 | 120.49 / 222.07 / 231.44 s | 232.48 s | 21.5 / 52 |

MQ 两轮结束时 RocketMQ 消费组均为 `Diff Total=0`、`Inflight Total=0`。5,000 条 MQ 到期窗口 ECS CPU 中位约 99.5%，Worker 约占 1.75 核、Broker 约 1.14 核，I/O 等待约 0；这是偏 CPU 的排空路径。扫描轮的落盘呈约 200 条一批的阶梯，与 [Worker 每轮上限 200 条、固定延迟 5 秒及 2 秒宽限](../../../peergrab-worker/src/main/java/com/peergrab/worker/TimeoutScanJob.java)一致。5,000 条扫描轮 CPU 中位约 16%，I/O 等待约 10%，磁盘忙碌约 43%；它更受串行批次/调度和落盘开销约束。两种路径都在 5,000 条下正确完成，但机制和资源瓶颈不同，不能把表中比值称为单一组件的独立“加速倍数”。峰值是某个到期后 1 秒桶内的**数据库持久化状态变化数**，不是 HTTP QPS，也不等于 RocketMQ 消费位点积压。扫描 5,000 条轮于 2026-09-27 00:00（北京时间）跨日完成。
