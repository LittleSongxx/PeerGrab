# PeerGrab ECS 同机压测与消融 · 2026-09-26

本轮只压 `peergrab-bench-*` 独立栈的 `127.0.0.1` API。公开站点只接受低频健康检查。下列数字是 **4 vCPU ECS 上生产服务同时运行时、带资源配额的同机基线**，不是公网容量或独立发压机测得的系统上限。

## 环境与门槛

| 项目 | 实际配置 |
| --- | --- |
| ECS | 4 vCPU、约 14 GiB RAM、10 Mbps 公网；Ubuntu 24.04、Docker 29.1.3、Compose 2.40.3、Java 21 |
| 生产 | `peergrab-prod` 7 个容器持续运行；部署提交 `f38a773` |
| 压测 | 独立项目、MySQL/Redis/RocketMQ 专属卷，全部端口绑定 `127.0.0.1`；工具源码提交 `f2cd6b1` 加本报告随附的执行器 |
| 运行镜像 | app `sha256:0fe9d367…`（与生产同一业务镜像）；S1–S4 Worker `sha256:a525c1d…`；S5 Worker `sha256:c6a77a5…`（从 `f2cd6b1` 源码打包） |
| 压测容器配额 | app 0.75 CPU / 1.5 GiB，MySQL 0.5 CPU / 1.5 GiB，Worker 0.25 CPU / 1 GiB，RocketMQ Broker 0.5 CPU / 1.5 GiB，另有 Redis/NameSrv 配额 |
| 停机门槛 | 生产健康异常、可用内存低于 3 GiB、宿主 CPU 连续两次超过 85%、IO 等待超过 10%、客户端拒载或正确性失败即停止升档 |

每轮先核对 Docker 项目标签、配置文件、回环端口、三个卷与 `bench_guard`；运行后核对业务数据库结果。不同配置的写入场景使用新项目与新卷。S2 只读线程池对照保持同一数据库与数据卷，仅重建**隔离 app**，并核对其他容器 ID 与应用 CPU/内存配额不变。

## S2：任务广场固定到达率

数据集是 10,000 条 `PUBLISHED` 任务，请求固定为首屏 `size=20`；每档预热 10 秒、采样 30 秒。`completed`、`ok` 均等于表中的 `offered`，错误和本地拒载均为 0。

| offered/s | 采样请求 | P50 | P95 | P99 | `run_id` |
| ---: | ---: | ---: | ---: | ---: | --- |
| 5 | 150 | 12.643 ms | 30.153 ms | 72.561 ms | `20260926-165421` |
| 10 | 300 | 9.090 ms | 14.003 ms | 21.201 ms | `20260926-165523` |
| 20 | 600 | 6.998 ms | 15.833 ms | 45.138 ms | `20260926-165625` |
| 40 | 1,200 | 5.746 ms | 24.727 ms | 54.295 ms | `20260926-170034` |
| 80 | 2,400 | 4.942 ms | 41.923 ms | 62.663 ms | `20260926-170136` |
| 160 | 4,800 | 4.565 ms | 58.215 ms | 85.064 ms | `20260926-170238` |

这些档位按顺序在同一应用上运行，JVM 与客户端逐步预热，因此低档 P99 不应解释成“负载越高越快”。320 RPS 档在约 8 秒时因宿主 CPU 连续采样 86.11% / 91.70% 被中止，`run_id=20260926-170537` 标为 `FAIL`；**没有 320 RPS 的有效容量结果**。应用重建后直接运行 160 RPS 曾出现客户端在途名额拒载；把名额从 32 增至 64 后仍偶发 1/4,800 次发压端调度错过。后续消融选择稳定无丢请求的 80 RPS，且全部使用相同的 64 个在途名额。

隔离库的 `EXPLAIN ANALYZE` 显示查询使用 `idx_campus_status`，首屏 20 行索引读取约 0.6 ms。测量期间 InnoDB 物理读次数没有增加，连接数峰值约 27；因此本轮没有依据去扩 MySQL buffer pool 或 `max_connections`。该固定首屏工作负载不能代表深翻页或大工作集。

### 连接池与 Tomcat 工作线程消融

每次重建 app 后先以 20→80 RPS 预热；下表只统计其后的 **两轮正式 80 RPS**，每轮 2,400/2,400 成功、零本地拒载和服务端错误。序列为 A／B／A／C／A，数据库、Worker、镜像、任务种子和容器配额保持一致。

| 顺序 | Hikari 最大连接 | Tomcat 最大线程 | 两轮 P99 | 中位 P99 | MySQL 结束连接数 |
| --- | ---: | ---: | --- | ---: | ---: |
| A1 | 20 | 200 | 54.033 / 38.543 ms | 46.288 ms | 14 / 14 |
| B | 8 | 200 | 59.712 / 40.229 ms | 49.971 ms | 11 / 11 |
| A2 | 20 | 200 | 53.962 / 39.199 ms | 46.581 ms | 14 / 15 |
| C | 20 | 64 | 55.398 / 46.021 ms | 50.710 ms | 14 / 14 |
| A3 | 20 | 200 | 55.768 / 36.886 ms | 46.327 ms | 12 / 12 |

两种缩小配置都没有观察到可信的延迟或吞吐收益；Hikari 8 在本轮少占约 3 个 MySQL 连接。每组第一轮普遍比第二轮慢，应用 CPU 配额节流也更重，**两轮不足以给 3–4 ms 的 P99 差值下优劣结论**。连接池并非越大越好，须结合活跃/等待连接与数据库并行能力测量：[Hikari 官方池大小说明](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)、[Tomcat HTTP Connector 线程配置](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)。当前应用未暴露 Hikari pending 或 Tomcat busy 指标，因果归因仍受限。

## S3：任务详情缓存消融

每个配置使用全新卷、相同 100 条任务；50 线程各请求 100 次。第一轮包含应用与缓存冷启动，第二轮表示该项目的热状态。全部轮次均为 5,000/5,000 成功。

| 配置 | 第一轮 RPS / P99 / 回源 | 第二轮 RPS / P99 / 回源 |
| --- | --- | --- |
| 缓存关闭 | 96 / 1,090 ms / 5,000 | 147 / 766 ms / 5,000 |
| 缓存开启，4 片 | 119 / 1,714 ms / 100 | 189 / 513 ms / 0 |
| 缓存开启，1 片 | 118 / 1,568 ms / 100 | 201 / 500 ms / 0 |

热状态下，4 片缓存相对关闭缓存的完成率约高 29%、P99 约低 33%，MySQL CPU 中位值从约 9% 降至 0.7%；Redis CPU 略升。冷状态的缓存开启轮 P99 较高，不能只展示热缓存收益。1 片与 4 片各只有一轮热状态结果，差异不足以确定优胜者；当前是**单节点 Redis**，不能外推 Redis Cluster 的扩展收益。

## S4 资金与 S1 抢单正确性

S4 通过 HTTP 完成发布、抢单、确认、取件、送达，再计时结算；同一任务重复结算 8 次，并附带取消退款与仲裁退款。TPS 分子取数据库持久化结算任务数。全部轮次账本借贷差额、系统账户快照差额与全局资金差额均为 0，托管单和退款数准确，系统错误为 0。

| 独立任务 / 线程 | 持久化结算 TPS | 结算请求 P99 | `run_id` |
| --- | ---: | ---: | --- |
| 5 / 2 | 2.61 | 1,095 ms | `20260926-180619` |
| 20 / 4 | 8.28 | 675 ms | `20260926-180724` |
| 50 / 8 | 12.29 | 974 ms | `20260926-180837` |

50 / 8 档期间 InnoDB 行锁等待增加 52 次、累计约 6.6 秒。不同任务仍共用发单人、跑腿人与系统托管／佣金钱包行；增加连接或线程可能只增加锁等待，不能把该结果当成一般钱包吞吐。

| S1 同任务并发 | 抢中 / 系统错误 | P99 | 数据库校验 |
| ---: | --- | ---: | --- |
| 16 | 1 / 0 | 393 ms | 31 条任务含预热，超卖 0、坏状态 0、流水差额 0 |
| 64 | 1 / 0 | 1,177 ms | 同上 |
| 128 | 1 / 0 | 2,198 ms | 同上 |

S1 是同一任务的瞬时竞争；`请求数 ÷ 爆发耗时` **不是稳态 QPS**。

## S5：自然到期与扫描间隔消融

每轮 100 条未来到期任务、`confirmSeconds=5`、`leadSeconds=30`；MQ 与扫描使用不同新栈。每个配置先处理一批 100 条，再比较第二批；所有轮次均 100/100 完成，提前处理、重复事件、卡单与错误最终状态均为 0。

| 独占通道 | 首批 P99 | 第二批 P50 / P95 / P99 | 第二批 `run_id` |
| --- | ---: | --- | --- |
| 兜底扫描 5,000 ms | 15.130 s | 5.415 / 8.093 / 8.517 s | `20260926-191633` |
| 兜底扫描 1,000 ms | 22.149 s | 9.031 / 11.669 / 11.933 s | `20260926-191041` |
| MQ 定时消息，扫描关闭 | 15.603 s | 5.842 / 9.840 / 9.940 s | `20260926-192429` |

独立探针 Topic 的 2 秒定时消息实际投递误差为 +834 ms；MQ 业务组在两批结束时 `Diff Total=0`、`Inflight Total=0`。MQ 第二批在到期后首个采样点（约 0.6 秒）已有任务落盘，5 秒扫描约在第 3–4 秒开始；但 Worker 仅有 0.25 CPU 配额，100 条批量流转的尾延迟仍达约 8–12 秒。1 秒扫描未在这次**单轮热状态对比**中取得收益；多轮重复和持续 Broker 积压采样尚缺，不能宣布 5 秒间隔或 MQ 通道全局最优。业务 `LOCKED` 数是待处理量，不等于 RocketMQ 消费位点积压。

## 结论与证据

- 当前配置下，**详情缓存开关**的热状态效果最明显；Hikari 20→8 与 Tomcat 200→64 在 80 RPS 首屏查询中没有可信的性能收益。
- [S2 列表查询](../../../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcErrandQueryAdapter.java)直接读 MySQL，[S3 详情查询](../../../peergrab-application/src/main/java/com/peergrab/application/usecase/query/GetErrandDetailUseCase.java)才经过缓存，不能拿 S2 做缓存消融。
- S4 的[共享钱包过账](../../../peergrab-application/src/main/java/com/peergrab/application/usecase/WalletPosting.java)、S5 的[顺序批处理扫描](../../../peergrab-worker/src/main/java/com/peergrab/worker/TimeoutScanJob.java)与 CPU 配额，比盲目加大线程池更值得下一轮测量。
- 生产健康检查在压测前后均返回 200；S5 一轮结束时出现过一次 684 ms 的健康响应，随后连续 10 次均恢复至约 40–80 ms。没有直接向公开域名发压。
- 所有一次性压测容器与专属卷已核对后销毁；最终 `docker compose ls` 只剩 `peergrab-prod`，生产镜像和数据库未替换。

原始 `bench_run` 摘要、逐档资源 JSONL、客户端日志和 A/B manifest 保存在本地忽略目录 `peergrab-backend/bench/runs/ecs-20260926-evidence.tar.gz`，SHA-256 为 `ca142e367e92a508e7082feef47053369e8c58a6315eda16fee0562d6795b310`。正式独立发压机测试、持续 Hikari/Tomcat 指标、深翻页工作集和每配置多轮重复仍是下一阶段；本报告不作为生产容量承诺。
