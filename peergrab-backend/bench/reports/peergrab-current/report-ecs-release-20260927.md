## S2：任务列表固定到达率

同机脚本对 `GET /api/errands?campusId=1&status=PUBLISHED&size=20` 每档预热 30 秒、采样 60 秒，5 秒超时、最大在途 128。`offered` 是计划发送，`sent` 才是实际发出；`schedulerMissed` 是客户端调度漏发，不能算作服务端拒绝。

| 同机目标 RPS | 采样 offered / sent / 成功 | P99 | 判定 |
| ---: | ---: | ---: | --- |
| 50 | 3,000 / 3,000 / 3,000 | 6.449 ms | PASS |
| 100 | 6,000 / 6,000 / 6,000 | 5.231 ms | PASS |
| 200 | 12,000 / 11,992 / 11,992 | 4.692 ms | FAIL：客户端 `schedulerMissed=8` |

200 RPS 档服务端没有错误，但脚本依零漏发规则停止扫档；400、800 RPS 的**同机档位没有执行**。这些毫秒级延迟只代表回环直连，不能替换公网请求延迟。

随后独立工作站通过 SSH 转发发压；每档预热 20 秒、采样 60 秒，5 秒超时。表中 P99 针对已发请求，所有已发请求最终成功；采样窗口内完成量略低于最终完成量，尾部请求在窗口后返回。

| 异机目标 RPS | 采样 offered / sent / 成功 | 客户端漏发 | P99 |
| ---: | ---: | ---: | ---: |
| 100 | 6,000 / 6,000 / 6,000 | 0 | 72.622 ms |
| 200 | 12,000 / 11,999 / 11,999 | 1 | 81.751 ms |
| 400 | 24,000 / 23,997 / 23,997 | 3 | 71.405 ms |
| 800 | 48,000 / 47,915 / 47,915 | 85 | 70.357 ms |

异机 400/800 RPS 预热期还分别漏发 1/52 个请求。因此可以陈述“800 目标档实际发出的 47,915 个请求全部成功”，**不能陈述“800 RPS 发足且零错误”**。SSH 加解密、转发和客户端调度均参与测量；本轮没有测出该版本完整公网路径的稳定容量上限。

## S4：持久化结算和 S1：同单抢单

S4 先为不同任务完成发布、抢单和履约，再并发结算。TPS 只取数据库中独立任务最终 `SETTLED` 的数量除以结算阶段耗时；P99 是结算请求延迟，不含准备阶段。每档另对同一任务发起 8 次重复结算、执行取消与仲裁退款，并用 SQL 检查资金和名额不变量。

| 独立任务 / 客户端线程 | 持久化结算 TPS | 请求 P99 | 独立结算 / 系统错误 |
| ---: | ---: | ---: | ---: |
| 20 / 4 | 43.38 | 125.7 ms | 20 / 0 |
| 50 / 8 | 42.29 | 328.9 ms | 50 / 0 |
| 100 / 16 | 44.64 | 591.4 ms | 100 / 0 |

三档同任务重复结算均为 1 次落盘、7 次业务拒绝；取消和仲裁退款、全局借贷平衡、系统户快照、钱包总额及单名额无超卖检查均通过。MySQL 行锁等待计数各档增量为 25、56、106 次，但包含造数及核验阶段，不能全部归因于并发结算。随着线程数增加，TPS 未明显上升而 P99 增大；这只是该共享演示钱包和同机客户端下的观察，不能外推真实用户钱包分布。

S1 的 16、64、128 人同时竞争一个名额，三档都恰好 1 人成功、0 超卖、0 系统错误；P99 分别为 61、197、304 ms，数据库交叉校验通过。S1 是一次性竞争尖峰，`请求数 ÷ 运行时间` 不作为稳态吞吐。

## S3：缓存消融

在独立新卷中对相同的 100 条任务详情读负载分别关闭（a）和开启（b）Redis 缓存；每轮并发 50、5,000 次请求，冷/热两轮各一次，全部成功且无写操作。缓存开启后的冷轮有 113 次 DB 加载，热轮 0 次；关闭缓存两轮均为 5,000 次 DB 加载。

| 模式 | 冷轮 RPS / P99 / DB 加载 | 热轮 RPS / P99 / DB 加载 |
| --- | ---: | ---: |
| 关闭缓存 a | 472 / 268 ms / 5,000 | 680 / 181 ms / 5,000 |
| 开启缓存 b | 435 / 528 ms / 113 | 661 / 163 ms / 0 |

这轮证明了**热缓存减少数据库加载**，却没有证明吞吐提升：热轮 661 RPS 低于无缓存的 680 RPS。两组仅各跑一次、冷启动状态不同，不能据此计算稳定加速比；读写混合、热 Key 和多轮统计仍需单独测试。

## S5：统一到期时刻后的持久化流转

两个**全新独立栈**各建立 1,000 条 `LOCKED` 任务，预先写入同一未来 `confirm_deadline_at`；延迟从预定到期时刻算到数据库首次持久化状态变更。MQ 轮关闭 Worker 超时扫描以归因于定时消息；扫描轮关闭 MQ，Worker 扫描间隔 5 秒、每轮批次上限 200。两条路径是不同机制对比，不能按单变量消融计算“加速倍数”。

| 路径 | 完成 / 预期 | 到期后 P50 / P95 / P99 | 最迟完成 | 错误不变量 |
| --- | ---: | ---: | ---: | ---: |
| MQ 定时消息 | 1,000 / 1,000 | 5.771 / 8.784 / 9.058 秒 | 25.820 秒 | 漏单、重复、提前、错误状态均 0 |
| 数据库扫描兜底 | 1,000 / 1,000 | 22.739 / 39.002 / 39.472 秒 | 39.594 秒 | 漏单、重复、提前、错误状态均 0 |

MQ 轮结束后单次 RocketMQ 消费进度快照显示确认超时 Topic `Diff Total=0`、`Inflight Total=0`。扫描轮每批约 200 条的阶梯与扫描配置相符。记录中的 `peakBusinessBacklog=1000` 是尚未流转的业务任务数，不是 RocketMQ 消费积压。本轮各只有一次 1,000 条样本，不证明故障期间或更大规模下的稳定排空时延。

首次 S5 探针造数没有写入本版服务要求的持久截止时间字段，结果无效；修正探针提交 `7da0a92`、重新建立空卷后才得到上表两轮 PASS。无效轮不进入性能结论，也不把它归因于生产 Worker 故障。
