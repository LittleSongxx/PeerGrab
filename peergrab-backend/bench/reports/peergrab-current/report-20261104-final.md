## 1. 环境与版本

- 代码基线：`5c1ecec`（`release/p12-grab-and-edge-hardening`）。
- 服务机：阿里云 ECS，8 vCPU / 14 GiB，单机 Docker Compose；基准测试期间生产栈停止。
- 发压机：4 vCPU / 7.4 GiB，Vegeta 固定到达率；部分 Go 脚本在本机汇总。
- 隔离栈：`peergrab-bench-*`，MySQL 8 / Redis 7 / RocketMQ 5 独立卷；测后销毁。
- 读容量：隔离 bench app + 生产同款 Hikari 50 / Tomcat 400；MySQL `max_connections=300`；S2 种子 10,000 条 PUBLISHED（campus=1，`size=20` 热页）；HTTP（无 TLS），异机发压。
- S4：同一隔离栈，`FundsHttpLoadClient` 准备阶段串行发布/抢单/确认/取货/送达，结算阶段计时；Hikari 50 / Tomcat 400。
- 自动结算：隔离栈，worker 1s 扫描、批 500；`AutoSettleTimelineProbe` 只测 Worker 到期→状态日志，不含 HTTP。
- 故障注入：S6 smoke 脚本，暂停单节点 25–30s；生产栈停止，只作用隔离栈。
- 测试基线：350 项后端测试 / 93 项 IT（2026-10-28 同一命令口径）；本报告只复验其中两个资金/幂等 IT。

## 2. 读容量

### 2.1 最终曲线（Hikari 50，60s × 3）

| 目标 RPS | 实际 RPS | 0 错误轮次 | 最差轮 P99 | 说明 |
|---:|---:|---|---:|---|
| 2450 | 2450.0 | 3/3 | **122.0ms**（典型 12.8/14.4ms） | 0 错误上限；第 3 轮有单次 454ms 尖刺 |
| 2500 | 2438.3/2487.7/2487.0 | 0/3 | 663.2ms | 每轮 2 次传输超时；不可称稳定 |

- 2450 三轮 transportErrors 均为 0；2500 每轮 2 次，属于明确的失败点。
- **不要写“2500 稳定”**；2450 是当前 0 错误上限，且最差轮有 122ms 尾。
- 2400 更保守；本轮未单独跑 2400×60×3。

### 2.2 Hikari 池对比

| 配置 | 2450 RPS（30s） | 2500 RPS（30s） | 结论 |
|---|---|---|---|
| Hikari 50 | P99 11.7ms | P99 15.6ms | 基线可用 |
| Hikari 100 | P99 242.4ms，实际 2440.8 | P99 242.0ms，实际 2464.8；2525 起 2 次错误 | **更差，不采用** |

- 结论：保持生产 Hikari 50；HikariCP 官方建议小池 + 线程等连接（8 核公式约 16–20，50 已偏大）。扩池不是读容量优化方向。
- 读容量测试为单接口热页、HTTP、单一 campus/首屏；不是全站容量，也不能与 2026-09 的 HTTPS/JMeter 数字直接比较。

## 3. S4 HTTP 结算

### 3.1 最终结果（多跑腿钱包 + 生产同款池）

| 档位 | durableSettledTps | P50 | P95 | P99 | 正确性 |
|---|---:|---:|---:|---:|---|
| 200 任务 / 32 线程 | **218.62** | 123.7ms | 231.0ms | **247.8ms** | 0 系统错误/0 重复，PASS |
| 500 任务 / 64 线程 | **387.70** | 151.4ms | 221.6ms | **254.7ms** | 0 系统错误/0 重复，PASS |

- DB 校验：settled 201/501（含同任务夹具）、refunded 2、badLedger 0、globalDebitCredit 0、systemSnapshotDiffs 0、totalDelta 0。
- 同任务 8 次尝试：7 次幂等拒绝、1 次入账。
- 两档均约 0.9–1.3s 短批次，**不是稳态 TPS**；同机 app+发压端，数字只作当前配置下界/对照。

### 3.2 优化前后（只作因果说明，不作为简历主数字）

| 配置 | 200/32 | 500/64 |
|---|---|---|
| 单跑腿 2001、bench Hikari20/Tomcat200 | 90.2 TPS / P99 428.7ms | 77.4 TPS / P99 1260ms |
| 512 跑腿钱包、Hikari50/Tomcat400 | 218.6 TPS / P99 247.8ms | 387.7 TPS / P99 254.7ms |

- 原 90/77 TPS 的主要瓶颈是**同一个跑腿 USER 钱包锁竞争**，不是每单账户模型失效；多跑腿后 TPS 提升 2.4–5 倍。
- 若简历只保留最终数字，使用 218.6/387.7，并注明短批次、同机、多跑腿夹具。

| 5s 扫描 / 批 100（旧默认证） | 10.682s | 22.538s | 22.572s | 1000/1000、0 重复 |

| **1s 扫描 / 批 500（已上生产）** | **3.156s** | **11.271s** | **11.307s** | **1000/1000、0 重复、资金差 0** |

- P99 从 22.6s 降到 11.3s（约 -50%）；主要收益来自减少扫描页数/周期，不是单笔结算变快。
- 口径：scan-only、单轮、隔离栈；worker 配置已应用到生产 `docker-compose.tune.yaml`。

## 5. 故障注入

### 5.1 Redis 暂停

| Redis 超时 | 暂停期间 250 次详情读 | P95 | max | 错误 |
|---|---:|---:|---:|---:|
| 500ms（旧） | 250 | 507.947ms | 519.057ms | 0 |
| **100ms（已上生产）** | 250 | **107.532ms** | 116.778ms | 0 |

- 暂停约 25s；抢单由 MySQL CAS 裁决成功；恢复后资金不变量全 0；S6 PASS。
- 100ms 会更早回源 DB，需观察高负载下 DB 回源压力；本次 10 RPS 故障负载下安全。

### 5.2 Broker 暂停

- Broker 暂停 30s；结算请求约 **180ms** 返回；DB 在暂停开始后 19ms 为 SETTLED。
- 恢复后 `fund_event_outbox` 约 2.7s 转 SENT；2 条通知；3 条结算流水；资金差 0。
- 单笔、单节点、30s；不代表持续积压/排空或 HA 能力。
