# ECS 上当前镜像的 JMeter 压测实测（2026-09-28）

本报告记录把 **HTTP 发压改由 Apache JMeter 5.6.3 执行后**，在阿里云 ECS 隔离维护窗口取得的新结果。它不是把[此前 Vegeta／Java／Python 的实测](report-ecs-spectrum-20260928.md)改名，也没有测出全站最大稳定容量。JMeter 负责 S1、S2、S3、S4 与 S6 的 HTTP 请求；S5 的对象是 Worker 定时消息和扫描，**本窗口没有重新运行 S5**。S6 只重测了 Redis 暂停下的详情 HTTP 负载，没有重跑 Broker 暂停结算故障。

## 环境、数据和计量口径

- 被压测的是 **8 vCPU、100 Mbps 的 ECS**。维护窗口停掉生产 `peergrab-prod`，每组业务场景使用经守卫检查的独立 `peergrab-bench-jm-*` Compose 项目、新 MySQL／Redis／RocketMQ 数据卷，逐项目清理。应用与 Worker 使用先前上线的 `5ace500` 业务镜像，镜像 ID 分别为 `sha256:387c3ec4139df1053a2505f42d5214284935ab8c98573c77df7cffb93725a0c2` 与 `sha256:40df63e12308802fd50d3da4b4142b5ae56eb173796b946e5b0a0beeb7960177`。这轮主要更换压测工具与计划，没有把负载结果误作业务代码优化收益。
- **S2 在异机**用 JMeter CLI 经公网 HTTPS、宿主 Nginx、隔离前端 Nginx 到 API，测试广场真实游标首屏。S1／S3／S4／S6 的 JMeter 在 ECS 上走宿主回环 API，故不能与 S2 的公网延迟直接比较。详情见[JMeter 入口与各场景分工](../../jmeter/README.md)。
- S2 的 10,000 条同校区已发布任务、固定用户和 `GET /api/errands?campusId=1&cursor=&size=20` 经前后身份校验；JMeter 对每个响应核验 HTTP 200、业务 `code=OK`、20 条列表和游标。JTL 分开统计采样开始数、HTTP／业务断言失败、连接等非 HTTP 错误。表中的 P99 是 **JMeter HTTP 采样耗时**；它不包含定时器等待或同步起跑前的排队。每档另有预热，以下数字只算正式采样窗口。
- S2 经校准后采用 **128 个可复用连接的用户线程 + Constant Throughput Timer**。这是以目标 RPS 调节固定用户池的发压方式；如果线程被慢请求占满，实际发出率可以低于目标，**不能称为严格开放到达模型**。报告因此同时列目标、实际开始数、时间窗口与错误数。S1 使用 Synchronizing Timer 集中释放线程，但实际采样起始跨度另报；S3／S4 是封闭式有限批次，均不是长时间稳定 QPS。
- 本轮有效 S2 的 JMX SHA-256 为 `f4b361fc3bde05b58a9941ffaf25b55c8979dd61e135d68e13782d22a501a3c4`；正式新栈读写混合的修正 JMX 为 `6325573e4ed66e9697bc28157299c47436b67c36e938f5670bbd6365cf2f92ba`。它们在维护窗口内迭代后实测，不能把最早错误计划的数字混入有效轮次。之后对进程组清理与故障读断言的安全收紧也不回写既有测量。
- 压测工具入口初始提交为 `dbd3b4f`，有效的 S2／S3 修正 JMX 及维护后收紧的安全门禁归档于 `8da6c37`；前两项以上述逐文件 SHA 绑定真实执行版本。生产 API／Worker 始终使用 `5ace500` 对应镜像，没有在压测中重建业务镜像。

## S2：公网广场游标首屏

最早的 Open Model 100 RPS 校准轮共留存 4,000 条 JTL，**每条都有正的 `Connect` 耗时**，出现 28 次 `SocketException` 和 5 次 `ConnectTimeoutException`，且停止阶段中断在途样本。`Connect > 0` 提示连接建立开销，但不能作为新建 TCP 连接的精确计数。它反映这份初始发压计划和目标场景的连接模型不匹配，**不计作应用在 100 RPS 已失稳**。改为固定用户池和连接复用为主的计划后，先做短档，再做 180 秒长档；每轮有单独 20 秒预热。

| 目标与正式采样 | 开始／HTTP 200 | 非 HTTP 错误 | 实际开始率 | 客户端 P50／P95／P99 |
| --- | ---: | ---: | ---: | --- |
| 450 RPS × 60 秒 | 27,024／27,024 | 0 | 450.40/s | 39／55／66 ms |
| 600 RPS × 60 秒 | 36,048／36,048 | 0 | 600.80/s | 39／50／62 ms |
| 600 RPS × 180 秒，轮 1 | 108,193／108,193 | 0 | 601.07/s | 42／58／88 ms |
| 600 RPS × 180 秒，轮 2 | 108,141／108,140 | **1 次连接超时** | 600.78/s | 42／60／72 ms |
| 500 RPS × 180 秒，轮 1 | 90,002／90,002 | 0 | 500.01/s | 40／52／112 ms |
| 500 RPS × 180 秒，轮 2 | 89,753／89,753 | 0 | 498.63/s | 40／169／245 ms |
| 500 RPS × 180 秒，轮 3 | 89,853／89,853 | 0 | 499.18/s | 39／62／255 ms |

600 RPS 长档前两轮共开始 **216,334** 次请求、216,333 次 HTTP 200、**1 次 `ConnectTimeoutException`**；异常轮触发停止条件，因此**没有第三轮 600 RPS**，不能写成“600 RPS 三轮零错误”。该错误 JTL 的连接耗时约 5,004 ms，响应码为非 HTTP；对应 Nginx 完成请求日志不能证明其已进入应用。500 RPS 三轮共开始 **269,608** 次并全部 HTTP 200，但实际开始率分别为 500.01、498.63、499.18/s，而 P99 从 112 ms 升至 245／255 ms。因此较稳妥的表述是“**这三个 180 秒窗口在约 499–500 次／秒实发下零请求错误，观察到尾延迟抬升**”，不能以零错误推出长期 SLA 或容量上限。

发压端 500 RPS 长档的 JMeter 进程最大 RSS 约 637–649 MiB、FD 295，采样 CPU 中位约单核 14%；三轮每秒开始数各约 445–522，未见整秒空档或显著补发突刺。ECS 的 2 秒资源采样按正式窗口过滤后，500 三轮宿主 CPU 中位 **35.57%／34.77%／32.69%**，公网发送中位约 **21.1 Mbps**；600 两轮 CPU 中位 **39.58%／39.83%**，发送中位约 **25.5 Mbps**。600 第一轮资源文件仅覆盖该 180 秒窗口的 **75 个**采样点，第二轮覆盖 88 个，不能把第一轮 CPU 中位当完整时段值。按完成时间附近过滤的脱敏 Nginx 日志对应五个长档仅记录 HTTP 200，服务端 `$request_time` P99 依次约 **30／32／21／42／30 ms**；日志含边界处预热／收尾请求，不能与 JTL 数量逐条对账。客户端超时与较高的客户端 P99 需要继续用连接阶段和端到端追踪定位，不能只看应用处理时间下结论。

上述单一广场首屏、固定身份和连接池设置不能推广到后续游标、多用户混合、写请求或全站。JMeter 500 与此前 Vegeta 600 的连接、定时及请求实现不同，**不计算跨工具的性能提升／回退百分比**。

## S1：同一名额尖峰

每档以不同跑腿身份和独立请求 ID 抢一个名额，正式放行前预热发布／抢单路径，JMeter `Synchronizing Timer` 同步起跑。数据库验收各档均为恰好 1 人抢中、1 个名额被占、无超卖；`SLOT_FULL` 和 `GRAB_CONFLICT` 是预期业务拒绝，不算系统错误，但它们的等待时间仍计入客户感知延迟。

| JMeter 线程／尝试 | 抢中／名额满／冲突／系统错误 | HTTP 采样 P50／P95／P99 | 样本开始跨度 | 整批完成时间 |
| ---: | --- | --- | ---: | ---: |
| 16 | 1／10／5／0 | 208／243／243 ms | 3 ms | 0.244 s |
| 128 | 1／121／6／0 | 593／772／789 ms | 53 ms | 0.796 s |
| 500 | 1／496／3／0 | 1,673／2,893／2,942 ms | 554 ms | 2.954 s |
| 2,000 | 1／1,994／5／0 | 4,719／7,889／**8,735 ms** | **2,228 ms** | **8.869 s** |

2,000 线程档有 **1,917 条 `Connect > 0` 的 JTL 样本**；该数不等同于准确的 TCP 新建连接数。即使定时器同时释放线程，请求实际开始也跨越 2.228 秒；不能说“2,000 个请求在同一瞬间抵达服务器”，更不能把 `2,000 ÷ 8.869` 称作可持续抢单 TPS。该轮资源窗口的宿主 CPU 采样峰值约 99.52%，但缺少逐请求连接和线程排队分解，无法把 P99 完全归因于数据库锁。

## S3：缓存开关、热 Key 与读写混合

缓存关／开分别在独立栈上对同一规模的 100 个预置任务执行连续三批，每批 50 线程 × 100 次详情读，均为 5,000/5,000 HTTP 与业务成功。相邻三批共享 JVM、连接和热度，**不构成三组独立冷启动样本**。

| 配置 | 三批详情 P99 | 三批详情回源 | 三批详情缓存命中 | MySQL `Com_select` 窗口增量 |
| --- | --- | --- | --- | ---: |
| 缓存关闭 | 246／164／129 ms | 5,000／5,000／5,000 | 0／0／0 | 30,460 |
| 缓存开启 | 479／170／116 ms | 100／0／0 | 4,900／5,000／5,000 | 15,526 |

`Com_select` 在此窗口下降约 **49.0%**，但它是 MySQL 实例级计数，包含鉴权和后台查询，不能说数据库总查询归零。缓存冷态首批 P99 为 479 ms，高于关闭缓存的 246 ms；第三批的 P99 差距也不能直接解释为稳定吞吐增益。已热缓存下另做 90% 请求集中到同一详情 Key 的 5,000 次读取，全部成功，缓存命中 5,000、详情回源 0、P99 **105 ms**；没有多分片或不同 Key 竞争的对照，不能证明热 Key 扩展能力。

首次读写混合 JMX 生成有误，实际只发出 **500 发布 + 450 读取**，因此不作为目标“每发布一次读 9 次”的结果。纠正计划后先用 200 发布 + 1,800 读取验证流程，再在**新隔离栈**做正式 500 发布 + 4,500 读取：5,000/5,000 成功，详情回源 621、命中 3,879，抽样缓存状态差异 0，混合样本 P99 **1,193 ms**。P99 同时包含发布和详情读，不能当作纯读 P99；抽样零差异也不证明所有并发时刻强一致。

## S4：并发结算与资金真值

经真实 HTTP 先完成任务发布、抢单、确认、取件、送达，准备耗时不计入结算批次。JMeter 用 32 线程结算 200 个不同任务，再对另一同一任务并发尝试 8 次。不同任务 **200/200** 成功，重复尝试 **1 次结算成功、7 次业务拒绝**，非 HTTP 与系统错误为 0；最终数据库中 201 个任务持久结算、201 个托管单释放。

200 单不同任务的短批次耗时 **5.761 秒**、持久完成率 **34.72 TPS**，采样 P50／P95／P99 为 **604／983／1,081 ms**。资金借贷、系统户快照、托管闭环、结算幂等和金额守恒均通过。相同窗口的 MySQL `Innodb_row_lock_waits` 从 0 增至 **205**、累计 `Innodb_row_lock_time` 增 **68,442 ms**；它覆盖准备、不同任务结算和重复尝试，不能除以 200 当作单请求锁等待。发布者／跑腿者共享钱包使这轮是热点账户短批次，**34.72 TPS 不是长期稳定结算容量**。

## S5 与 S6：本轮覆盖边界

**S5 没有新 JMeter 实测。**同刻到期的主要工作发生在 Worker、RocketMQ 与扫描任务，不是一个 HTTP 接口的吞吐；此前 1,000 单 MQ／扫描对照仍按[原始探针及原工具报告](report-ecs-spectrum-20260928.md)标注，不能换标为 JMeter 成绩。当前[JMeter 场景分工](../../jmeter/README.md)明确保留定时事件造数、状态日志和数据库校验。

**S6 本轮只执行 Redis 暂停演练。**JMeter Open Model 以约 10 次／秒发起详情读，暂停前／期间／恢复后分别 50／180／50 次，全部 HTTP 200 且业务成功、无传输失败，P95 为 **137／2,109／105 ms**。Redis 容器实际暂停约 **27.0 秒**；暂停期间一笔真实抢单由数据库裁决，名额及资金 SQL 校验通过。这说明本次单节点暂停中详情读可回源，但 P95 达 2 秒量级；它既非 Redis 集群切换测试，也没有证明数据库在更高失效流量下不会被打穿。ECS 本轮使用的 S6 JMX SHA-256 是 `656d8800a4cb6b09e2833fd2029f5038c969e7fd7f771408af517d8d1e1b0f3c`，逐条验证 HTTP、业务码与允许状态；随后增加的同任务 ID 断言和更严格的发压量门槛只在本地假服务验证，**不能追认为本轮 ECS 已执行的断言**。此前默认配置下 **Broker 暂停后结算已提交、客户端 8 秒超时** 的问题未在本窗口重跑或修复，仍以[先前故障实测](report-ecs-spectrum-20260928.md)为准。
