# 校招／实习：项目取舍与面试讲述方案

目标：每个主线设计都能解释业务原因、实现方式、失败边界和验证证据，并能自然展开 Java／Spring／MySQL／Redis／MQ 基础。本文先记录取舍依据，再以源码和测试的最终状态为准。

**2026-09-27 落地状态。** 本轮已把资金消息切到新建的普通 Topic，补隔离 CI 的真实 Broker 契约检查；自动任务以持久截止时间和数据库 CAS 裁决；递补成功后删详情缓存并写持久通知，回退扣分入事务；信用重建按事件顺序回放；两类 outbox 使用带 token 的租约领取和单调终态。消息与详情缓存改用 Jackson；资金事务统一由应用用例拥有；未启用的 ShardingSphere 代码单列实验模块。JWT 删除重复的 JTI 撤销表，过期会话由 Worker 分批清理，Snowflake 租约失效影响 readiness 并按生产配置退出重启。正常缓存默认单键、Bloom 关闭，错误失效顺序只留在测试中。

以下是**本轮不应凭空实施**的升级项：ES/Canal、多级缓存、Redis Cluster、分库分表、Seata、XXL-JOB、独立 Leaf 服务和支付接入都缺少当前业务需求或容量证据。MySQL 候选表替换 Redis 候选租约、改自增/号段 ID、Spring Security/Session 协议切换也涉及数据与前端迁移，应先用候选人数、请求负载、故障目标和迁移演练定方案；当前保留正确性保护，并将它们作为面试时可解释的升级门槛。

阅读范围是用户指定的 [面经目录知识图谱](../../面经/Java后端开发面试知识图谱.html) 和 [面经目录真实面试报告](../../面经/纯Java后端_真实面试题与备考报告.html)，没有用根目录同名副本代替；技术事实以当前工作区为准。

**结论：保留少数有证据的难点，把没有收益的基础设施复杂度减下来。**

对校招／实习，建议项目主动讲三条主线：单名额抢单与同库资金正确性、Outbox／延迟任务可靠异步、SQL 与缓存性能验证。Spring 事务代理、线程池与故障隔离作为两条辅助展开线。自研发号租约、认证撤销协议、多片缓存和候选租约不宜同时抛成简历亮点。

业务状态机、账户锁序、条件更新、幂等键是应用本来就需要实现的业务规则；Outbox 是成熟模式的轻量落地。它们不会因为“代码自己写”就成为造轮子。反而是手写 JSON、重复的状态协议、没有实际启用的生产依赖，应优先收敛。

**两份报告对准备方向的支持与限制。**

真实面试报告的“2026 纯 Java 样本中的频率核算”将 MySQL 查询、Redis 缓存、MQ 可靠交付、隔离级别宽题族列为 H3；线程池工程边界、Spring AOP、Redis 分布式锁列为 H2。它明确限定原帖岗位、年份、来源等级和作者去重；标签不是全国出现概率，细项不能继承宽题族频次。JD 的技能要求也不参与面经频次。

知识图谱的“06 访问路径与事务可见性”“07 缓存一致性”“08 异步业务结果”与项目直接匹配；“00 面试怎么考”“01 项目与交付”强调真实规模、个人职责和指标依据。其问题节点包含作者串联和延伸题，部分 source 链接是合集；不能把 DOM 节点数或公司标签数说成独立真实面试场次。

两份文件的样本和题族划分不同，不应机械合并 H 标签。尤其：真实面试报告明确 ES 细项没有达到本轮纯 Java A 级原帖逐问证据；Canal 500ms 精确问法只有单帖 L1，多级缓存也有岗位语言未明的旁证。因此没有依据为了“高频覆盖”给这个项目增加 ES、Canal 或本地缓存层。

**设计取舍清单。**

| 当前设计 | 校招／实习建议 | 解释成本与最小改造 |
| --- | --- | --- |
| 手写 JSON 拼接和字符串切片解析 | 直接换 DTO／record + Jackson | 项目已依赖 Jackson，没有“少引库”的收益。固定消息 DTO、字段校验和 schemaVersion 更易说明，也能测试未知字段、非法格式和大整数 ID。 |
| ShardingSphere 规则实验处于运行依赖 | 移至独立实验模块或非默认 profile | 运行时仍是普通单 MySQL DataSource，不能称为已落地分库分表。保留实验和选型记录即可，避免生产依赖替未启用功能付成本。 |
| 单片／多片／generation 指针／Bloom 多条缓存分支 | 生产主线只保留单键 Cache Aside | 当前默认单片、Bloom 关闭。多片和 Bloom 放实验；只保留 TTL 抖动、短空值、一套重建机制、提交后失效和明确的失败重试。状态新鲜度先定目标，再决定是否需要逻辑过期。 |
| afterCommit + 固定双删 + 随机校验 + 错误顺序开关 | 统一正常失效链路，错误模式移测试 | 双删是降低竞态概率，不是强一致证明。可复用 outbox 做删除失败重试，TTL 作兜底；随机抽检是运维工具，不当作同步协议。BEFORE_COMMIT 对照放测试替身，避免出现在正常生产配置中。 |
| JWT + DB session + refresh + jti 撤销表 | 先删除无独立语义的冗余撤销层 | 当前登出已撤销整个 sid，再记录单个 jti 不增加有效语义。短期保留 Bearer 接口并去冗余；若整体整理鉴权，选 Spring Security + Spring Session JDBC，保持 Redis 故障不影响会话的目标。切换 Cookie 需同步处理 CSRF、Cookie 属性、前端与 WebSocket 契约。 |
| MySQL Snowflake 节点租约与时间栅栏 | 修好安全恢复，退出主动简历叙事；后续评估简化 | 同时涉及租约、单调时钟、墙上时钟、旧节点时间水位和数据库失败，很难只靠“雪花算法位分配”回答。单库重构时优先评估自增；必须事前取得 ID 才评估号段。现存 ID/关联数据要迁移设计，不能直接删保护或改固定 workerId。 |
| Redis 候选四键租约 | 保留业务，优先评估 MySQL 候选表 | 四键和 claim token 有真实宕机恢复作用，不能退回会丢候选的 ZPOPMIN。校园候选量若不大，可用有序候选表、唯一键和任务同事务更新减少跨存储协调；需确认入队负载。Redis Streams FIFO 不能直接替代信用加权排序。 |
| 资金 outbox、延迟 local_message、扫描失败重试 | 保留可靠性，统一领取和确认约定 | 三者有不同事实含义，不必强行合表；但 claim token、租约、退避、终态和指标应统一。不要再扩成自研通用工作流平台，也不用 XXL-JOB 替代业务幂等。 |
| 资金适配器开事务并回调业务、业务又嵌套 TransactionTemplate | 事务归应用用例拥有 | 推荐外层负责完整事务重试，独立事务 Step 写状态、资金、信用和 outbox；基础设施端口负责持久化。对展示通知使用统一提交后事件，可靠消息仍入 outbox。 |
| 自研枚举状态机、Money、WalletPosting | 保留并重点讲 | 状态合法性、整数分、借贷相等、条件扣减和固定锁序直接对应业务不变量，代码规模可控。无须为有限状态流转上通用状态机框架。 |
| JdbcTemplate 与显式 SQL | 可以保留 | CAS 和 affectedRows、锁语句、索引和执行计划都易于展示。没有必要只为 MyBatis 关键词改 ORM；若选 MyBatis，则用明确 Mapper SQL 保留这些语义，不用通用 CRUD 掩盖并发规则。 |
| WebSocket 跨副本分发、信用榜单、仲裁 UI | 作为辅助功能 | 用它们展示完整业务体验；避免同时自称推送平台、权限平台和推荐系统。WebSocket 可丢、持久通知可补读的边界必须讲清。 |

关键代码证据：[发号租约](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/config/JdbcSnowflakeNodeLease.java)、[JWT 实现](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/auth/JwtAuthAdapter.java)、[详情缓存](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/cache/RedisErrandCacheAdapter.java)、[候选租约](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/cache/RedisCandidateQueueAdapter.java)、[资金事件持久化](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcFundEventOutboxAdapter.java)、[运行依赖](../peergrab-infrastructure/pom.xml)。

成熟替代的边界：项目已有 Jackson，直接使用其 [POJO 数据绑定能力](https://github.com/FasterXML/jackson)即可；[Spring Session 3.5 JDBC](https://docs.spring.io/spring-session/reference/3.5/guides/boot-jdbc.html)提供关系库持久会话，不需要自造会话表协议；[Spring 6.2 事务事件](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/event.html)能绑定 AFTER_COMMIT，但不提供持久投递，不能替代 outbox。美团 [Leaf](https://tech.meituan.com/2017/04/21/mt-leaf.html)可以作为号段和时钟问题的方案对照；当前没有理由额外部署 Leaf/ZooKeeper 服务。采用依赖时应跟随现有 Spring Boot 3.5 的版本管理，不照搬最新大版本的配置。

**适合校招的目标主线。**

保持 Spring Boot 模块化单体，API 和 Worker 分进程；MySQL 是任务和资金唯一事实源；Redis 用于详情缓存、热点限流辅助和可重建榜单；RocketMQ 负责异步通知和延迟唤醒。业务需要手写明确的 SQL、状态校验与事务，不需要手写 JSON、认证底层和更多框架协议。保留现有模块边界，不必为了讲解再重排整个 Maven 工程。

对于已经增加的可靠性机制，先合并重复表达并补故障闭环，再考虑迁移。校招目标不能成为删除幂等、防重、事务或超时恢复保护的理由；让正常方案简洁，把可选实验和替代方案单独保存。

**三条主故事：每条都留一个自然追问入口。**

| 主故事 | 可以主动说的一句话 | 面试官可继续追问 | 准备证据 |
| --- | --- | --- | --- |
| 抢单与同库资金正确性 | “同一个任务只有一个名额，Redis 预占后仍需 MySQL 条件更新和唯一键裁决；资金在同库内按固定账户顺序加锁。” | Lua 原子性范围；Redis 成功而 DB 失败；CAS／行锁；RC/RR；当前读与快照读；死锁；重复请求；提交结果未知 | 一条 CAS SQL、一张事务时序图、并发抢单及资金不变量测试 |
| Outbox 与延迟任务可靠性 | “业务事务里先登记事件，Worker 再发送；发送成功而确认前退出会重发，所以按业务号幂等。” | ACK 丢失；至少一次；重复/乱序；死信；积压；事务消息替代；MQ 早到/迟到；扫描兜底 | outbox DDL、状态图、真实 Broker 集成测试、重复消费与进程退出实验 |
| 查询与缓存优化 | “我用执行计划和扫描行数验证索引；流水按时间和 ID 组合游标，展示缓存允许明确的短暂陈旧窗口。” | B+树；联合索引；回表；OFFSET；同毫秒排序；Cache Aside；穿透/击穿/雪崩；热点和大 Key | 同负载 A/B/A SQL、游标边界测试、缓存开关对照与延迟分布 |

两个辅助展开点：

- “为什么单独拆事务 Step Bean？”→ Spring AOP 代理、自调用、传播行为、异常与回滚、afterCommit。自调用失去的是被调用方法的代理事务语义；已有外层事务并不会凭空消失。
- “为什么在线服务和后台任务分开？”→ 线程池资源隔离、队列上限、拒绝策略、Hikari 等待、超时预算、CPU/GC/连接排障。用实际池和指标举例，不为讲 AQS/JMM 增加无用线程或伪造线上 OOM。

这些路线分别对应知识图谱的 sql-index/sql-plan/sql-mvcc、redis-cache/redis-lock、mq-reliability/mq-idempotency、spring-tx，以及真实报告 JQ-02、JQ-05、JQ-06、JQ-07、DB-05/06 和 JAVA-04。图谱中部分链路是作者综合编排，面试时只能作为准备路线，不能说成某家公司一定如此追问。

**30–45 秒开场示例（能力需与最终验收状态同步）。**

> 这是一个个人校园跑腿交易项目，包含发布托管、单名额抢单、履约、退款和仲裁。我主要围绕三个问题做设计：并发下谁能抢中、重复请求会不会重复动账，以及缓存和异步消息失败后怎样恢复。任务和资金由 MySQL 本地事务裁决，Redis 用于读加速和降低竞争性写入，通知通过 outbox 异步投递。优化时记录执行计划、扫描行数和压测延迟，也做了重复请求与依赖故障测试。

展开时任选一条主故事，不一次列出所有组件。每个钩子准备“正常路径—失败时序—测试证据—升级条件”四层；面试官转问别的基础问题时正常回答，不试图把每题强行拉回预设脚本。

**必须修正的说法。**

- 项目公开 API 只支持单任务一个名额，不称通用多库存抢购系统。
- 当前 Lua 之前已读任务、信用、在途数；不能重复源码里“绝大多数失败请求不访问 DB”的注释。可说减少竞争性写入，但收益比例要有对照测量。
- 资金使用本地事务＋outbox；不能说当前用 RocketMQ 事务消息实现资金跨服务强一致，不能承诺端到端 exactly-once。
- 未启用的 ShardingSphere、ES/Canal、多级缓存和多机集群只能讲评估/实验。阿里 Sentinel 应用限流与 Redis Sentinel 容灾需区分。
- `shards=1`、Bloom 关闭是当前默认；500ms 双删不能保证 500ms 内必然一致。
- 数据库行锁不是 Java AQS，Redis Lua 原子执行也不是 Redis 与 MySQL 的联合事务。
- 本地十万流水的查询毫秒结果是隔离实验，不称线上 P99 提升若干倍；650 QPS 是旧版本单接口三分钟验证档，不称全站稳定容量。没有真实用户量就说个人部署和压测。
- 使用 AI 辅助开发可以坦诚说明。用户需要能独立定位核心 SQL/事务边界、解释失败用例并完成小改动；报告明确出现了 AI 交付后谁验收的追问。

**建议修改顺序。**

1. 先修上一轮审查的真实契约缺口：普通 outbox 消息与 TRANSACTION Topic 不匹配、压测 token 缺 sid/会话、CI JWT 示例缺项、系统操作未验证 deadline、递补漏删缓存、租约失效未进入健康/恢复流程。它们不能靠“面试不主动讲”回避。
2. 做低风险减法：DTO/Jackson；移出未运行分片依赖、缓存多片/Bloom实验和故意错误开关；统一事务归属及消息确认约定。保留有意义的回归实验。
3. 对鉴权、ID、候选持久化分别写短 ADR 后再迁移；若临近面试，优先修恢复边界并备好图，不做大面积协议/数据模型更换。
4. 每条主故事整理一页证据卡：业务约束、两种候选方案、选择原因、关键 SQL/时序、一个失败窗口、一项实际测试、升级条件。至少保留一段并发问题和一段性能问题由自己现场解释与修改。

“能说清楚”的验收不是背完一段讲稿：用两分钟解释为什么需要；用五分钟画出路径；能指出最终正确性由哪条 SQL/事务/唯一键保证；能回答进程在某一步退出会怎样；数据指标有条件和分母。达到这些标准的三个难点，足以形成清晰可信的校招项目主线。
