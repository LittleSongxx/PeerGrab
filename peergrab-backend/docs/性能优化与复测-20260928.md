# PeerGrab 性能优化与单轮复测 · 2026-09-28

本轮针对[高延迟与超时定位报告](高延迟与超时定位报告-20260928.md)中的可确认问题实施了小范围修改，并在 ECS 上对**每个版本和场景分别建立全新隔离栈、各跑一轮**作对照。结论是：**S5 扫描兜底的批量积压延迟下降；S1 的重复调用减少，但秒级尖峰延迟没有被根治；S4 本轮变慢，不能宣称结算性能改善。** 本轮没有复测 S2 公网 HTTPS，也没有证据宣称公网偶发超时已解决。以下数字不能替换多轮、同条件的[上线基线](../bench/reports/peergrab-current/report-ecs-release-20260927.md)或[简历专项指标](../bench/reports/peergrab-current/report-resume-metrics-20260927.md)。

## 改动及选择理由

应用与 Worker 改动提交为 [`5ace500`](https://github.com/LittleSongxx/PeerGrab/commit/5ace500bdd11a6079c46b056e654b57a99c0ff62)：

- [抢单用例](../peergrab-application/src/main/java/com/peergrab/application/usecase/GrabErrandUseCase.java)复用本次资格校验读到的信用分，为候选入队计算优先分；候选流转时仍重新校验资格。Redis 候选入队 Lua 已返回包含队列及租约的总数，[端口与适配器](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/cache/RedisCandidateQueueAdapter.java)现在直接返回该值，省去旧版随后调用 `size()` 发出的两条独立 `ZCARD` 命令。原有字段 `candidateRank` 的语义是**入队时队列总数**，并非个人排序名次。
- [结算用例](../peergrab-application/src/main/java/com/peergrab/application/usecase/SettleErrandUseCase.java)在提交后读取一次骑手信用分，供排行榜与通知共同使用；不改变资金事务边界。新增有界标签的鉴权解析、抢单用例结果、钱包行锁获取和信用行获取／事件回放计时，用于后续按阶段定位。计时覆盖代码段，并非 MySQL 内部纯锁等待时间。
- [尖峰发压器](../peergrab-bench/src/main/java/com/peergrab/bench/SpikeLoadClient.java)把每个虚拟线程的结果写入独立槽位，分别报告放行到 `send`、`send` 到响应、放行到响应，以及按业务结果分桶；预热没有建立 2,000 条并发连接。
- [超时兜底扫描](../peergrab-worker/src/main/java/com/peergrab/worker/TimeoutScanJob.java)在一次调度内连续处理至多 5 批、每批至多 200 条，新增 10 秒运行预算；失败重试仍另有单轮 50 条上限。这样减少大批任务同刻到期时每 200 条额外等待一次 5 秒调度间隔，同时给同池其他任务留出运行机会。时间预算到期后的任务由下次调度续扫。相关单元测试随提交更新。

## 同条件对照结果

| 场景与口径 | 旧版单轮 | 新版单轮 | 能得出的结论 |
| --- | ---: | ---: | --- |
| S1：2,000 人、1 名额；成功／满额／冲突／限流／错误 | 1／1,983／3／13／0 | 1／1,999／0／0／0 | 两轮均无超卖、无系统错误；结果构成不同。 |
| S1：`send` 到完成 P50／P99 | 2,663／4,385 ms | 2,652／4,154 ms | P99 单轮低 231 ms，不能据此宣称稳定提升。 |
| S1：放行到 `send` P50／P99；放行到完成 P99 | 932／1,871；5,506 ms | 857／1,635；5,502 ms | 客户端调度／建连相关阶段仍很长，整体尖峰尾延迟基本未变。两段 P99 不是同一请求，不能相加或相减归因。 |
| S1：满额请求 `send` 到完成 P50／P99 | 2,652／4,390 ms，n=1,983 | 2,653／4,155 ms，n=1,999 | 满额分支有小幅尾部下降，但仍是秒级。 |
| S4：200 个不同任务、32 并发，持久结算 TPS；全尝试 P99 | 41.89 TPS；1,182 ms | 32.34 TPS；1,346 ms | 新版这轮**更慢**；单轮且热点锁争用波动大，无法归因于改动或判定真实回退幅度。两轮资金核验均 PASS。 |
| S5：1,000 条同刻到期、扫描兜底；完成数；到期后 P50／P99／最大值 | 1,000/1,000；22,901／39,466／39,577 ms | 1,000/1,000；11,918／23,330／23,436 ms | P99 单轮下降 16,136 ms（约 40.9%）；仍有约 23 秒尾部，不能称实时。 |

S1 的 `send` 时间包含客户端连接、请求与响应。新版新增的应用计时显示，1,999 个满额请求在**鉴权之后的抢单用例内**累计 792.537 秒，均值约 396 ms，观测最大约 952 ms；鉴权解析在覆盖 S4 造数与 S1 的整个窗口共 3,281 次、累计 54.106 秒，均值约 16.5 ms。应用 HTTP 抢单计时 2,232 次（含 S4 造数、S1 预热和正式请求），总计旧版 864.350 秒、新版 850.417 秒。由于缺少跨客户端与服务端的逐请求 ID 对齐，不能把这些聚合指标直接相减并命名为“Tomcat 排队耗时”；秒级客户端延迟仍须用连接／首字节跟踪验证。

旧／新版完整的 **S4 造数、S4 正式请求、S1 预热与 S1 正式请求的合并窗口**中，Redis `ZCARD` 计数 7,932 → 3,998（少 3,934 次，约 49.6%），MySQL `Com_select` 增量 25,563 → 23,464（少 2,099），Hikari 获取连接次数增量 21,150 → 19,053（少 2,097）。方向与消除候选分支重复查询一致；**这些不是单独 S1 的调用数**，也不能把全部差额精确归因给某一个代码点。新版同一窗口钱包锁获取计时 437 次、累计 98.929 秒、观测最大 734 ms；信用行获取 202 次、累计 0.442 秒，信用事件回放 202 次、累计 0.369 秒。MySQL `Innodb_row_lock_time` 旧／新版为 75.788／97.786 秒，`Innodb_row_lock_waits` 均为 206。这些累计值包含并发等待与 S4/S1 混合活动，不能当作单个 S4 请求的耗时；但与共享钱包热点锁竞争的机制相符。下一轮应单独截取 S4 正式阶段，并重复交错测试共享／分散钱包，才可评价结算修改与瓶颈份额。

S5 新版时间线约在到期后第 3–13 秒完成前 571 条，第 14–17 秒未新增完成，第 18–24 秒处理余下任务；这与**有界运行时间后等待下次调度**相符。新旧两轮均无未处理、重复、提前或错误状态。本探针以 `errand_status_log.created_at` 计算时差：该值在事务内写入，**不是精确的提交可见时间**，所以 39.466 → 23.330 秒仅是同口径状态日志时间对照，不能解释成事务提交时刻或用户端实际收到通知的 P99。[探针源码](../peergrab-bench/src/main/java/com/peergrab/bench/S5TimelineProbe.java)。

## 正确性、部署与证据边界

S1 数据库不变量核验两轮 PASS；S4 两轮各 200 个不同任务成功持久结算，重复结算被拒，账本不平衡、系统账户快照差异与总金额变化均为 0。S5 的隔离库初始无流水，旧版[资金核验 SQL](../bench/scripts/verify_fund.sql)对空集 `SUM` 得到 `NULL`，曾误报 L1 `FAIL`；随后用 `COALESCE(..., 0)` 修正，空账本显示借贷 0／0、`PASS`。这是**校验器空集误判**，不是资金不平衡，也不属于 `5ace500` 的应用改动。默认本地 `mvn -q test` 通过。随后在隔离的本地 MySQL/Redis 上运行 `mvn -B -ntp -Dpeergrab.it=true test`，命令退出码 0、`BUILD SUCCESS`；逐模块 Surefire 汇总为 223 个执行、0 失败、0 错误、0 跳过，测试容器和数据卷已清理至 0。测试目录残留 6 份旧 XML 报告，因此不使用跨轮 XML 累加数作为完整 IT 结果。
