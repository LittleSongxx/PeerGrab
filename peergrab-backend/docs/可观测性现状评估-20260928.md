# PeerGrab 可观测性现状评估 · 2026-09-28

结论：项目已经在 API 与 Worker 中埋入指标并暴露 Prometheus 格式，隔离 ECS 压测曾实际读取这两个端点；**生产 Compose 尚未部署持续抓取、历史看板、告警或分布式追踪后端**。因此当前可以做临时指标快照和日志排查，不能展示长期趋势、实时告警或跨 API→MQ→Worker 的完整调用链。本评估根据仓库代码与部署配置，不把测试环境的指标快照说成生产监控平台。

| 能力 | 已有实现 | 当前边界 |
| --- | --- | --- |
| 基础指标 | API 和 Worker 的 Actuator 暴露内部 `/actuator/prometheus`；Spring/Micrometer 提供 JVM、HTTP、连接池等基础指标。[API 配置](../peergrab-bootstrap/src/main/resources/application.yaml)、[Worker 配置](../peergrab-worker/src/main/resources/application.yaml) | [生产 Compose](../docker/docker-compose.prod.yaml)只有业务和中间件服务，没有 Prometheus、Grafana 或 Alertmanager；未配置持久采样和告警。 |
| 业务指标 | `Result.code` 计数、抢单与认证分结果耗时、钱包锁和信用事件耗时、缓存失效失败；Worker 每 15 秒采样资金 outbox、延迟消息、死信和对账差异。[抢单](../peergrab-presentation/src/main/java/com/peergrab/presentation/ErrandController.java)、[Worker 采样](../peergrab-worker/src/main/java/com/peergrab/worker/WorkerOperationalMetrics.java) | Worker 查询失败只写警告，Gauge 保留上次值；必须增加采样成功时间或错误指标，才能区分“确实为 0”和“采样停了”。 |
| 延迟分位数 | 抢单、认证等自定义 Timer 发布直方图。[抢单 Timer](../peergrab-presentation/src/main/java/com/peergrab/presentation/ErrandController.java) | 压测抓到的通用 `http_server_requests_seconds` 有 count/sum，未见 `_bucket`；现有导出不能计算**滚动全接口 P95/P99**。需要为选定低基数 HTTP URI 配置直方图与适当桶，再用 `histogram_quantile`；不能把累计均值当 P99。 |
| 健康检查 | 容器使用内部 readiness；生产 API 为 Redis 故障降级而在 readiness 中排除 Redis，Worker readiness 包含 Redis。[生产 Compose](../docker/docker-compose.prod.yaml) | 公开 [`/api/health`](../peergrab-presentation/src/main/java/com/peergrab/presentation/HealthController.java)固定返回 `UP`，只能检查该请求可达，不能代表 MySQL、Redis、MQ、积压或资金链路健康。 |
| 日志与追踪 | 应用日志写容器标准输出，可用 `docker compose logs` 排查；`X-Request-Id` 用于发布／抢单幂等。[部署说明](../docker/ECS_DEPLOY.md)、[请求入口](../peergrab-presentation/src/main/java/com/peergrab/presentation/ErrandController.java) | 没有集中日志检索／保留、统一关联 ID、MDC、`traceparent` 传播或 OpenTelemetry／Jaeger／SkyWalking 采集后端。**幂等键不是 trace ID**，不能直接复用其语义。 |

按当前单 ECS 规模，优先补三项即可形成可说明、可演示的闭环：

1. 在受限网络内抓取 API／Worker 指标并持久化，给 Grafana 做一张小看板：RPS、HTTP 错误率及延迟、JVM／Hikari、资金 outbox 最老待投递时长、延迟消息死信、对账差异和 scrape 存活。给关键异常配置少量告警；告警接收人和噪声阈值应按演示站实际运维能力设定。
2. 为通用 HTTP 请求启用有边界的直方图，验证 `_bucket` 确实导出，再显示滚动 P95/P99；URI 使用模板标签，不以任务 ID、用户 ID 或 requestId 做指标标签。Worker 采样另记录最近成功时间与失败次数，避免失效时显示陈旧的零积压。
3. 为一次请求生成独立关联 ID，按业务事件把它写入结构化日志，并在 outbox／消息元数据中延续至 Worker。只有当跨进程排障确有收益时，再引入采样式 Micrometer Tracing／OpenTelemetry 与轻量追踪后端；不需要为了简历先搭完整 ELK 与追踪集群。

Spring Boot 官方支持对指定指标配置 `percentiles-histogram` 和 SLO 桶；Prometheus 用直方图桶计算可聚合的滚动分位数，Spring Boot 也提供 Micrometer Tracing／OpenTelemetry 接入能力。[Spring Boot 指标文档](https://docs.spring.io/spring-boot/reference/actuator/metrics.html)、[Prometheus 直方图文档](https://prometheus.io/docs/practices/histograms/)、[Spring Boot 可观测性文档](https://docs.spring.io/spring-boot/reference/actuator/observability.html)。这些是可选实施方案，**不是本项目已部署的组件**。
