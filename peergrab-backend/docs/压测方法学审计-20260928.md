# PeerGrab 压测方法学审计 · 2026-09-28

本审计把图片当作检查清单，核对仓库中的**实际脚本、执行报告与原始证据口径**，不把图片中的六场景覆盖、六轮收益或故障矩阵当成事实。结论是：项目已有较扎实的隔离与资金／名额正确性校验；旧版 S2 同机高 QPS、S3 缓存一致性、S4 稳态 TPS、S5 提交延迟和 S6 故障恢复等说法需要收紧。目前**没有证据支持“六类压测已全部完成、六轮调优均取得收益”**。

## 图片中需要修正的推论

1. **`run_id` 是轮次标签，不是独立数据空间。** [记录器](../peergrab-bench/src/main/java/com/peergrab/bench/BenchRunRecorder.java)把任务挂到轮次，真正隔离依赖独立 Compose 项目、MySQL/Redis/MQ 卷和端口。[清理脚本](../bench/scripts/cleanup.sh)只销毁核验过的整套测试栈；某些阶梯在同一栈累积钱包、流水、信用事件，跨轮比较仍受历史状态影响。
2. **预热与稳态不能套固定“前 30 秒不算、尾 10 秒丢弃”。** S2 有单独预热和 180 秒采样，但[Vegeta 包装器](../bench/scripts/run_remote_s2_vegeta.py)只保留聚合 JSON，缺少逐秒请求／延迟原始时间线来验证窗口是否稳定；`-max-body=0` 仍读完响应体却不保留内容，因此压测中未验证每条 JSON 的业务含义。S1 是一次性尖峰、S3 要刻意测冷缓存、S5 测同刻到期，都不该按稳态读接口规则裁剪。Vegeta 官方说明目标速率与实际速率可能略有偏差，且 P99 聚合了**所有请求结果**，含失败请求，必须另外报告超时和状态分母。[Vegeta 官方说明](https://github.com/tsenart/vegeta)、[聚合实现](https://github.com/tsenart/vegeta/blob/master/lib/metrics.go#L676-L777)。
3. **“QPS 平台／P99 增长／错误抬头，任一项即容量上限”过于武断。** 旧版 S2 50 并发就已接近 100–400 并发的完成 QPS；固定并发客户端会随响应变慢自动降低到达率。容量判定须在同一业务负载、预设错误和延迟目标下核对计划到达、实际发送、窗口内完成、排队与客户端饱和，再重复验证。[k6 开放与封闭模型说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)、[Google SRE 对 QPS 与尾延迟的说明](https://sre.google/sre-book/service-level-objectives/)。
4. **“三层对账全过”有价值但非完整资金正确性。** 已实现全局借贷平衡、系统账户快照与托管状态检查，也有结算笔数／金额补充核验；全局 0 差额仍可能掩盖账户间错记或缺少应有的某笔交易。按每个业务号和任务核对付款人、收款人、金额、状态与流水唯一性，并在故障窗口结束后再次核对。[资金校验 SQL](../bench/scripts/verify_fund.sql)。
5. **反例必须按实际实验边界讲。** 历史错误实现确实压出了 Redis 名额负数与多个无条件更新结果，但 A 只破坏 Redis、B 再破坏数据库 CAS，是**故意做坏的对照实验**；原本运行实现没有这些超卖。[历史报告](../bench/reports/original-project/report-20260818-014200.md)。图片中的“六轮调优 QPS+20%、Redis+50%、错误 18%→0%、异步记账 500→200ms、虚拟线程省 350MB、GC 毛刺消失”不是本项目六轮实测。[早期方案 R1–R6 表](压测方案与容量评估.md)的收益列均为`[待补充]`；当前资金事务也未异步化。旧版 800 并发连接错误 146→0 的确有报告，但吞吐 6346→5205 QPS、P99 390→472ms，不能只讲错误下降。[P6/P7 旧报告](../bench/reports/original-project/report-P6-P7-20260822-complete.md)。

## 下一轮最小而正确的执行方案

不需要为满足图片而部署 JMeter、wrk、JMH 或额外集群；工具是否合格取决于**负载模型、发压端能力、指标分母和业务校验**。Apache JMeter 官方也要求真正发压使用 CLI、控制资源与监听器数量，并注意固定线程不足时的协调遗漏；已有 Vegeta 固定到达率和 Java 业务客户端可以继续使用。[JMeter 最佳实践](https://jmeter.apache.org/usermanual/best-practices.html)。

1. **先声明目标与版本。** 每个场景记录提交／镜像、CPU／带宽、入口路径、数据量及分布、用户与热点比例、到达模型、超时、预热停止条件、SLO 与退出门槛。把旧版同机、旧版 ECS、当前镜像分开，不把最高一次完成 QPS 命名为容量。
2. **S2 优先重测当前镜像的真实广场路径。** 异机固定到达率分别测 `cursor=` 首屏与下一页，保留旧 offset 路径作单独对照；造数达到目标工作集。记录每秒 `scheduled/sent/completed/HTTP 2xx/业务码/传输错误`、客户端 CPU／文件描述符／连接阶段和服务器 CPU、Tomcat、Hikari、MySQL、Redis；失败档保留限量脱敏原始时序。每档预热至指标稳定后多轮采样，至少给 3 个交错轮次；任何漏发或超时必须单列，不把错误从延迟图中悄悄删掉。用预先确定的延迟及错误门槛判定**已验证的负载区间**，再说拐点。[k6 阈值设计参考](https://grafana.com/docs/k6/latest/using-k6/thresholds/)。
3. **S1/S4 分开正确性与容量结论。** S1 用唯一用户抢同单验证超卖，另加同一用户同一 requestId 重放／重试；同时记录开闸→实际发送→服务端进入→完成，并校准 2,000 个连接的发压能力。S4 固定 200 任务、32 线程和完全相同的钱包／信用历史，分别跑共享钱包与分散钱包，交错重复 A/B；单独截取准备、结算请求和提交后阶段，查询 MySQL 行锁等待并核对每任务分账。短批次 TPS 与持续 TPS 分开命名。
4. **S3/S5/S6 只补有业务价值的缺口。** S3 先定义缓存命中率、详情回源数、MySQL 总 QPS 三种不同分母，再做同一任务 ID 的读写交错、冷态／预热态成对复测。S5 增加提交后独立连接的可见性观察、MQ 投递→消费→事务分段和逐秒积压；扫描／MQ 各在新栈重复。若简历或可用性目标要讲故障恢复，再选择 Redis、Broker、DB 池三类最关键故障，在隔离栈持续负载中注入，记录注入点、降级响应、排空时间与最终资金校验，不要求六类场景形式上全覆盖。

每轮使用[现有预检与清理入口](../bench/README.md)验证独立卷和回环绑定；`run_id` 保留作追溯，不能替代数据隔离。报告正文同时给出“已执行／未执行、最差轮次、失败档、反例与副作用”，与原始私有证据一一对应。
