# PeerGrab 压测方法学审计 · 2026-09-28

本审计把图片当作检查清单，核对仓库中的**实际脚本、执行报告与原始证据口径**，不把图片中的数字、六轮收益或完整故障矩阵当成事实。2026-09-28 随后在当前 `5ace500` 镜像上完成了 [ECS S1–S6 分场景复测](../bench/reports/peergrab-current/report-ecs-spectrum-20260928.md)：六类负载均有实测，但每类覆盖范围不同，S6 只验证 Redis 暂停与 Broker 暂停，且发现默认配置下一笔结算的客户端超时。**没有证据支持“六轮调优均取得收益”或“完成全故障矩阵”。**

## 图片中需要修正的推论

1. **`run_id` 是轮次标签，不是独立数据空间。** [记录器](../peergrab-bench/src/main/java/com/peergrab/bench/BenchRunRecorder.java)把任务挂到轮次，真正隔离依赖独立 Compose 项目、MySQL/Redis/MQ 卷和端口。[清理脚本](../bench/scripts/cleanup.sh)只销毁核验过的整套测试栈；某些阶梯在同一栈累积钱包、流水、信用事件，跨轮比较仍受历史状态影响。
2. **预热与稳态不能套固定“前 30 秒不算、尾 10 秒丢弃”。** S2 有单独 20 秒预热、180 秒采样，[Vegeta 包装器](../bench/scripts/run_remote_s2_vegeta.py)现保存约每秒的完成数与累计分位数快照，但没有每个请求的原始发出时间戳、连接阶段或响应 JSON；`-max-body=0` 读完响应体却不保留内容，所以只在压前／压后校验业务 ID。S1 是一次性尖峰、S3 要刻意测冷缓存、S5 测同刻到期，都不该按稳态读接口规则裁剪。Vegeta 官方说明目标速率与实际速率可能略有偏差，且 P99 聚合了**所有请求结果**，含失败请求，必须另外报告超时和状态分母。[Vegeta 官方说明](https://github.com/tsenart/vegeta)、[聚合实现](https://github.com/tsenart/vegeta/blob/master/lib/metrics.go#L676-L777)。
3. **“QPS 平台／P99 增长／错误抬头，任一项即容量上限”过于武断。** 旧版 S2 50 并发就已接近 100–400 并发的完成 QPS；固定并发客户端会随响应变慢自动降低到达率。容量判定须在同一业务负载、预设错误和延迟目标下核对计划到达、实际发送、窗口内完成、排队与客户端饱和，再重复验证。[k6 开放与封闭模型说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)、[Google SRE 对 QPS 与尾延迟的说明](https://sre.google/sre-book/service-level-objectives/)。
4. **“三层对账全过”有价值但非完整资金正确性。** 已实现全局借贷平衡、系统账户快照与托管状态检查，也有结算笔数／金额补充核验；全局 0 差额仍可能掩盖账户间错记或缺少应有的某笔交易。按每个业务号和任务核对付款人、收款人、金额、状态与流水唯一性，并在故障窗口结束后再次核对。[资金校验 SQL](../bench/scripts/verify_fund.sql)。
5. **反例必须按实际实验边界讲。** 历史错误实现确实压出了 Redis 名额负数与多个无条件更新结果，但 A 只破坏 Redis、B 再破坏数据库 CAS，是**故意做坏的对照实验**；原本运行实现没有这些超卖。[历史报告](../bench/reports/original-project/report-20260818-014200.md)。图片中的“六轮调优 QPS+20%、Redis+50%、错误 18%→0%、异步记账 500→200ms、虚拟线程省 350MB、GC 毛刺消失”不是本项目六轮实测。[早期方案 R1–R6 表](压测方案与容量评估.md)的收益列均为`[待补充]`；当前资金事务也未异步化。旧版 800 并发连接错误 146→0 的确有报告，但吞吐 6346→5205 QPS、P99 390→472ms，不能只讲错误下降。[P6/P7 旧报告](../bench/reports/original-project/report-P6-P7-20260822-complete.md)。

## 本轮已补与后续缺口

不需要为满足图片而部署 JMeter、wrk、JMH 或额外集群；工具是否合格取决于**负载模型、发压端能力、指标分母和业务校验**。Apache JMeter 官方也要求真正发压使用 CLI、控制资源与监听器数量，并注意固定线程不足时的协调遗漏；已有 Vegeta 固定到达率和 Java 业务客户端可以继续使用。[JMeter 最佳实践](https://jmeter.apache.org/usermanual/best-practices.html)。

1. **已明确版本、隔离和分母。** [当前 ECS 报告](../bench/reports/peergrab-current/report-ecs-spectrum-20260928.md)逐场景记录镜像、入口、数据、时长、错误分类与私有证据校验和；旧版同机、旧版 ECS 和当前镜像分开，最高短档不命名为稳定容量。
2. **S2 已测当前真实游标首屏，仍需补全业务分布和连接归因。** 异机固定到达率 600 RPS 做了三轮 180 秒，保留约每秒完成快照，第三轮 4 次传输超时单列。下一步应加入后续游标页、多用户及写入混合，保留逐秒计划到达／实际发送与有限脱敏原始请求，并做客户端、Nginx 双端连接阶段跟踪，才能判定超时原因及已验证负载区间。先定义可接受错误率与尾延迟门槛再测拐点。[k6 阈值设计参考](https://grafana.com/docs/k6/latest/using-k6/thresholds/)。
3. **S1/S4 正确性已重复，容量仍是另一件事。** S1 已记录开闸→发送→完成，证明同单不超卖；继续补同一用户同一 requestId 的负载重试及服务端入口时间。S4 已固定 200 任务、32 线程在两个新栈测共享钱包行锁，下一步以分散钱包同条件交错对照、逐任务分账核验、持续负载及事务内／提交后分段计时，才能谈稳态结算能力。
4. **S3/S5/S6 已有边界明确的基准，下一步聚焦故障修复。** S3 已区分详情回源、MySQL 总查询与缓存命中，并用新任务读写交错；仍需冷热态重复对照与逐请求一致性采样。S5 要补提交后可见性、MQ 分段时延及逐秒积压。S6 应先修复默认配置下 Broker 暂停造成的结算客户端超时并回归；再按价值补 DB 连接池耗尽、消息重复／延迟与长时间恢复，不把受限单节点实验写成 RPO/RTO。

每轮使用[现有预检与清理入口](../bench/README.md)验证独立卷和回环绑定；`run_id` 保留作追溯，不能替代数据隔离。报告正文同时给出“已执行／未执行、最差轮次、失败档、反例与副作用”，与原始私有证据一一对应。
