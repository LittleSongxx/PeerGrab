# PeerGrab 性能压测与架构决策方案

> 方案基线：2026-09-25。下文的实验矩阵是下一轮容量验证计划，除明确标注的短时冒烟外，不代表已经完成的现行容量实测。

> 状态：设计方案及 2026-09-26 评测资产更新。隔离栈预检、受控造数、场景客户端、只读资源采样和整栈清理已具备；当前版本仍未完成独立环境的正式容量压测。

已有[独立栈工具冒烟](../bench/reports/smoke-20260925-current.md)；2026-09-26 又在本地独立栈验证了 S2/S4/S5 链路。这些短试跑只检查工具与正确性，不用于推断容量。

## 1. 要回答的问题

PeerGrab 的容量不能用一个 QPS 数字描述。任务广场读取、热点抢单、发布托管、结算退款、到期流转和 WebSocket 推送消耗的资源不同，也有不同的正确性要求。本方案用可复现的分场景测试，回答以下问题：

1. 指定数据规模和流量比例下，各接口能稳定处理多少**到达请求**，P95/P99 与系统错误率是多少？
2. 并发、超时和故障出现时，名额、资金、任务状态和消息是否仍然正确？
3. 单 MySQL 基线何时遇到实测瓶颈；缓存、连接池、线程池、限流、Worker 等配置各带来多少收益及代价？
4. 在事先声明的响应时间、正确性和资源预算约束下，哪一组配置具有最低运行成本？

目前**不存在有证据支持的唯一「最优设计」**。下面的历史数据是旧代码、旧机器上的同机基线，不能直接作为当前 Docker 栈的容量承诺或分库依据。

## 3. 正确性前置门槛

先补能识别错误的测试，再比较优化版本。发现任何名额、资金或任务状态不变式失败时，该配置即使 QPS 较高也应淘汰。

- **抢单幂等与缓存恢复**：已把 `requestId` 持久化并绑定跑腿身份；只有数据库提交过的记录才返回重放成功。Redis 名额键缺失或过期时走 MySQL CAS 保证仍可抢；候选递补重新验证资格。完整的生产故障注入和恢复性能仍待独立压测。
- **资金流水真实性**：四种资金过账在事务内按账户 ID 升序锁行，用锁后余额写 `balance_after` 和 `account_version`；新增并发链校验。共享托管户与佣金户仍是待测锁热点，不能在未测量前决定分桶或分库。
- **发布重试**：`X-Request-Id` 按发布者持久化，占位、托管扣款与任务创建同事务提交；相同内容重放返回原任务，同键不同内容拒绝。Redis 名额与 Bloom 登记移到提交后，外部调用故障不会把已经提交的发布误报为失败。旧客户端若不传请求键仍无法跨请求去重。
- **轮次完整性**：新 [S4 HTTP 客户端](../peergrab-bench/src/main/java/com/peergrab/bench/FundsHttpLoadClient.java)经真实业务流程造数，检查结算数、托管单、资金流水和账户余额；[按轮校验](../bench/scripts/verify_run.sql)仍只覆盖部分抢单不变式。正式压测还须核对 Redis/DB、请求响应与 MQ 积压。

第一轮对比以**单应用实例、单 MySQL、Redis、RocketMQ、Worker**为基线。分片规则只有在运行链路真正接入且单库容量瓶颈经观测确认后，才作为下一轮候选；不得把规则文件存在等同于已测分片收益。

## 4. 隔离与防误操作

压测必须使用可销毁的独立 Compose 项目、MySQL 数据卷、Redis 实例、RocketMQ 数据和端口。数据库即使仍名为 `peer_grab`，也必须是**不同容器和不同数据卷**。不能对当前演示栈做造数、加压或清理。

现有入口按[运行手册](../bench/README.md)先执行 [`preflight.py`](../bench/scripts/preflight.py)：

1. 要求 `PEERGRAB_BENCH_DISPOSABLE=YES`、`peergrab-bench-*` 项目名，并核对运行容器、网络及三个持久化卷的 Compose 与专用压测标签。
2. API、MySQL、Redis 与 MQ 代理端口必须只绑定宿主机回环地址；应用和 Worker 必须指向同一项目的 MySQL、Redis 与 MQ 服务。被测 URL 必须是本机 HTTP 地址，当前不支持异机发压。
3. 压测库的 `bench_guard.project_name` 必须等于当前 Compose 项目名，API 健康检查必须成功。造数器、客户端及清理器各自重新运行预检。
4. [`seed_bench.py`](../bench/scripts/seed_bench.py)只在空任务表与空轮次表的全新栈中执行 S2/S3 一次性造数；[`cleanup.sh`](../bench/scripts/cleanup.sh)只在项目名二次确认后销毁该项目的容器、网络和专属卷。没有按轮或孤儿数据删除路径，也不会重置共享钱包。

旧 [`seed.sql`](../bench/scripts/seed.sql)、[`seed_s4.sql`](../bench/scripts/seed_s4.sql) 和 [`seed_s5.sql`](../bench/scripts/seed_s5.sql) 已禁用；历史报告和 Git 历史仍保留其旧实验口径。旧 S4 数据库集成测试会重置账户，只能在明确隔离的测试库运行，不作为运行中栈的造数入口。

压测身份应由独立库造数并预发有效 token；正式计时不包含登录。默认生产鉴权禁用 `X-User-Id`，[S1 客户端](../peergrab-bench/src/main/java/com/peergrab/bench/SpikeLoadClient.java)现要求独立 JWT 压测栈，并在计时前签发不同用户的 Bearer token。其他客户端可在计时前登录获取 token；测试后门仅用于隔离环境中的单独对照实验，不得混成主报告。

## 5. 分层场景矩阵

每个场景固定数据集规模、请求体、用户池、状态分布与结果集大小。建议至少记录小规模（1 万任务）与目标规模（例如 10 万任务）两档；具体目标规模需根据预期校园数量和业务量确认。列表必须包含首页、后续游标页以及有结果和无结果查询，不能仅重复同一个空查询。

| 层/场景 | 负载模型及开关 | 业务结果分类 | 退出时必须成立的不变式 |
| --- | --- | --- | --- |
| C0 功能基线 | 单用户依次完成发布→抢单→确认→取货→送达→结算；取消退款、仲裁各一轮，MQ/Worker 开启 | 每个步骤的 `OK` 与拒绝原因逐项核对 | 任务状态合法；发布扣款恰好一次，结算或退款恰好一次；通知最终可见。 |
| C1 热点抢单 | 1 单 2000 个不同跑腿瞬时释放；再测相同用户/`requestId` 重放及不同用户复用 ID；单任务限流开/关仅在隔离栈对照 | `OK`、`SLOT_FULL`、`GRAB_RATE_LIMITED`、`GRAB_CONFLICT`、`ALREADY_GRABBED` 为业务分类；5xx、超时和连接异常为系统错误 | 单名额任务 `slot_taken ∈ {0,1}`；当前轮 `GRABBED` 数与 `slot_taken` 一致且不超过 1；唯一 `grabber_id` 与记录一致；Redis 剩余名额与 DB 一致或已可自动重建；重复请求无额外资金/状态变化。 |
| C2 读容量 | 任务广场列表、我的任务、详情；冷/热 Key、不同页、不同结果大小；按**外部到达率**逐档升高 | 有数据与空结果分开统计；HTTP/业务码两层判断；401 不计入成功 | 返回数据与 DB 对应；缓存命中/回源计数一致，缓存校验差异为 0；无无限增长的连接、线程或堆。 |
| C3 分散写容量 | 多任务、多用户按到达率发布和抢单；例如 90% 读、10% 写另开混合场景；发布与抢单分别给出指标 | 发布 `OK`/余额不足；抢单业务拒绝；系统错误单独计数 | 每个任务单名额；托管额 = 发布悬赏；`GRABBED`、任务状态、Redis、候选队列及去重关系自洽。 |
| C4 资金全链路 | 经 HTTP 对多个任务并发结算；同一任务 200 请求；取消、仲裁与结算竞态；MQ 和对账 Worker 开启 | `SETTLED`/已处理冲突等业务结果与系统错误分开；TPS 分子只用实际成功结算数 | 借贷总额相等；所有账户前后总余额守恒；托管状态与任务终态、流水闭环；每个业务号对应唯一一组金额正确的流水；账户快照与 `balance_after` 可解释。 |
| C5 到期流转 | 按真实时间轴自然到期的任务流，以及 1 万条同秒到期突发；MQ 主通道和停 MQ 后兜底分开 | 已流转、已确认、回退、重试、卡单分开 | `到期时刻→持久化状态变更` 的 P50/P95/P99；零重复流转、零永久卡单、轮次不超过上限；消息积压在规定恢复窗口清零。 |
| C6 故障与耐久 | 稳态负载下短暂 Redis 延迟/重启、MQ 中断、MySQL 连接受限；另做 30–60 分钟稳定性测试 | 故障窗口和恢复窗口分别统计业务拒绝、系统错误、重试成功 | C1/C4 的名额和资金不变式持续成立；错误恢复后积压能排空，无持续内存或连接泄漏。 |
| C7 实时推送 | 分档建立 WebSocket 连接，再触发任务和资金事件 | 连接失败、推送失败、重复推送、重连分别统计 | 用户仅收到授权事件；推送延迟分布和丢失率达标；重连后能通过持久通知补读。 |

预期的「名额满」和热点限流不能记作服务器失败，但要单独保留数量；大量限流也不能伪装为「高吞吐成功」。对 C1/C4 必须同时核对客户端计数、数据库事实和 Redis/MQ 状态。数据库校验应作为自动验收步骤，而非报告中手填 `PASS`。

## 6. 加压方法与观测

- **稳态容量用开放到达模型**：给定请求到达率（例如 100、200、400、800 RPS，之后二分寻找边界），与上一次响应是否完成无关；分别记录 offered RPS、完成 RPS、在途量和超时。新增 `OpenLoopLoadClient` 可对固定任务广场 GET 做按绝对时钟发出的开放到达率分档，记录本地拒载、服务端拒载、窗口内完成数与含失败的延迟；它尚未覆盖混合业务和自动数据库校验。`RampLoadClient` 仍是封闭循环，仅用于资源饱和探索。
- **尖峰正确性用屏障释放模型**：C1 用同步开闸构造瞬时冲突，报告开闸到发出请求的时间分布；它只用于竞争与限流验证，不把「请求数 ÷ 一次尖峰耗时」称为稳态 QPS。
- **预热与复测**：每个构型先完成 JVM、连接池和缓存预热，至少 2 分钟；每档正式测量至少 3 分钟，排除前 30s 与最后 10s，至少重复 3 次，报告中位数、各次原值与波动。超过目标到达率后要继续测一个超压档，确认拐点；改变配置时先恢复相同数据快照并保持其他变量不变。
- **分位数与错误**：以完整请求耗时直方图计算 P50/P95/P99；成功、业务拒绝、HTTP 5xx、网络异常、超时分别输出。超时不能从 P99 样本中静默消失，须记录超时阈值、数量与被截断的延迟。每秒保留原始计数，避免只存一轮平均值。
- **资源观测**：现有 [`collect_metrics.py`](../bench/scripts/collect_metrics.py)按秒采集宿主机 CPU、内存、磁盘、网络和项目容器的 Docker stats、镜像及资源限制。正式容量测试仍需补齐 API 分路由、Tomcat/Hikari/JVM、Redis、MySQL 锁等待、MQ 积压和 Worker 延迟的持续指标；同机发压时记录其 CPU/网络并标明测量限制。
- **可复现元数据**：每轮记录 Git SHA 与工作树状态、镜像 digest、JDK/容器资源限制、机器 CPU/内存、MySQL 数据量/索引与缓存冷热状态、配置开关、用户池大小、请求比例、原始时间序列、直方图、SQL 校验输出和 `run_id`。报告只比较相同口径、相同数据快照的结果。

## 7. A/B 候选与决策顺序

先用单库基线定位瓶颈，再一项一项切换。表中「需新开关」表示当前代码不能直接运行该对照；任何实验都只在隔离栈进行。

| 顺序 | 基线与候选 | 比较目标及约束 |
| --- | --- | --- |
| A0 | 当前单 MySQL、Redis Lua + DB CAS、MQ/Worker 开启 | 建立 C0–C7 可复现基线，先通过正确性门槛。 |
| A1 | 详情缓存关/开、热点副本 1/4/8；现有 `peergrab.cache.enabled`、`peergrab.cache.shards` | 在相同热度和结果大小下比较 P99、DB 回源、Redis CPU 与一致性差异；不因「命中率高」就认定收益。 |
| A2 | Hikari 10/20/40；Tomcat 100/200/400，分别单变量变化 | 寻找吞吐、排队、DB 锁等待与 P99 的 Pareto 前沿；不以最大连接数为目标。 |
| A3 | 抢单限流阈值、Sentinel/local 对照；DB CAS-only 路径**需新开关** | 比较热点时系统错误、有效抢中、限流拒绝与资源消耗；始终保留 DB 正确性校验。 |
| A4 | Session/JWT；鉴权数据与 token 池一致 | 确认鉴权开销和会话存储成本，不与测试身份头模式混比。 |
| A5 | Worker 批量大小、扫描间隔；MQ 开启/故障兜底分开 | 比较到期延迟、积压清空速度、DB 压力；MQ 关闭的灾备结果不得与正常链路混成一个 TPS。 |
| A6 | 单库扩容、索引/SQL 改动；分片**仅在接入运行链路后** | 先确认数据库为主瓶颈、单库优化已达边界，并计入跨分片查询、迁移、运维成本；当前不预设分片胜出。 |

候选配置的比较应以**有效吞吐**和 P99 为横纵轴，同时标注 CPU、内存、数据库负载与总成本。某一方案仅提升峰值 QPS，却增加错误、资金风险或运维复杂度，不应自动胜出。

## 8. 决策记分卡与验收

开始前由产品/课程目标确定各接口的请求比例、目标在线人数、目标数据量、允许延迟与运行预算。若尚无外部目标，可临时使用「系统错误率 <0.1%、名额/资金差异为 0、S5 正常 MQ 到期 P99 <1s」作为**实验目标**，不能称为已达成 SLA；P99 上限还应按读、抢单、资金接口分别设定。

每一候选版本填写：

| 维度 | 取数与准入规则 |
| --- | --- |
| 正确性 | C0–C5 自动不变式全部通过；任一资金差异、超卖、重复结算、越权或永久卡单直接淘汰。 |
| 用户体验 | 在事先指定的到达率和数据规模下，各接口 P95/P99、业务成功率与限流量均达到各自目标。 |
| 稳定容量 | 连续 3 次稳态测试均达标；完成 RPS 与 offered RPS 接近，无持续增长的队列、GC 停顿、连接等待或 MQ 积压。取达标的最高到达率，不取超压档瞬时峰值。 |
| 韧性 | 故障窗口结果明确，恢复后在约定时间内排空积压且对账无差异。 |
| 成本与复杂度 | 记录应用/DB/Redis/MQ 实例数、内存、CPU、存储和维护复杂度；达到同一业务目标时优先更简单、成本更低的方案。 |

退出本轮优化的条件：单库基线和所有候选都有三次可复验报告；已找到满足业务目标的最低成本方案；再增配资源或引入新组件的边际收益低于其成本；留出容量余量并完成超压/故障验证。否则结论应写「当前证据不足」，附下一项需测的问题，而不是给出「最优」头衔。
