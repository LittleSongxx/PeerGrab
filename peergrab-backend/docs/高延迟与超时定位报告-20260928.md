# PeerGrab 高延迟与超时定位 · 2026-09-28

> 本文记录 **2026-09-28 较早维护窗口**对旧首屏路径和当时镜像的分层定位，保留当时证据，不当作当前镜像最终性能结论。随后 `5ace500` 镜像的[游标首屏与 S1–S6 ECS 分场景复测](../bench/reports/peergrab-current/report-ecs-spectrum-20260928.md)已完成：600 RPS 三轮长档第三轮仍有 4 次公网传输超时，Broker 暂停另暴露已提交结算的客户端超时。文中“游标请求仍需补测”指当时状态。

## 结论与证据等级

**当前没有证据证明「应用处理列表请求超过客户端超时时间」；本轮 650 RPS 公网列表测试的 3 次超时，定位在宿主 Nginx 已记录的 HTTP 请求处理之前。** 经 SSH 转发回环到同一 ECS、同一宿主 Nginx 443，保留 `www.peergrab.cn` 的 Host、SNI、证书和 TLS，650 RPS × 180 秒全部成功。因此宿主 TLS、Nginx HTTP 处理、前端代理、应用和数据库不是这 3 次公网超时的直接可见阶段；剩余候选包括发压端连接行为、本地出口或 NAT、运营商路径、ECS 公网 TCP 接入及握手前后的无完整 HTTP 请求情形。**尚未抓包或对失败连接建立跨端唯一关联，不能把责任定给某一方，也不能宣称 650 RPS 是容量上限。**

抢单的多秒客户端延迟是另一个问题：新一轮 2,000 人尖峰的客户端 P50/P99 为 3.117/5.153 秒，而应用的 HTTP 请求处理计时平均约 0.472 秒，记录的最大值约 1.042 秒。这**强烈提示**客户端连接、发送、Tomcat 接入／排队等应用计时之外的时间占较大部分；两组计时没有逐请求 ID 对齐，不可直接相减成某一层的精确耗时。抢单业务内部仍有重复 SQL/Redis 读，是可优化的次要贡献，尚未用分桶服务端计时量化。

## S2：公网超时被缩小到哪一段

基线是[简历指标专项复测](../bench/reports/peergrab-current/report-resume-metrics-20260927.md)：首屏任务列表、10,000 条 `PUBLISHED` 数据、`GET /api/errands?campusId=1&status=PUBLISHED&size=20`，工作站直连公网 HTTPS/HTTP/1.1，600 RPS × 180 秒 × 3 轮共 324,000/324,000 HTTP 200，最差轮 P99 256.232 ms；旧 650 RPS 长档有 23 次传输超时（旧工具记录数比计划多 1，不能精算错误率）。本轮新测试**不能覆盖旧结果**，说明错误具有时段／路径波动，需要多轮看概率及关联事件。

该压测 URL 未带 `cursor`，走[控制器的普通分页分支](../peergrab-presentation/src/main/java/com/peergrab/presentation/ErrandController.java)；当前[任务广场页面](../../peergrab-frontend/src/pages/Square.tsx)使用带空 `cursor` 的游标分支。两者经过相同公网代理，但 SQL 和响应结构不完全相同。公网超时发生在 HTTP 处理前的结论不依赖此差异，**600 RPS 的列表容量数字仍需补测真实页面使用的游标请求**。

本轮同镜像隔离栈、同请求和 650 RPS × 180 秒，各有 20 秒预热，分母核对如下：

| 路径 | 采样 `offered`／结果／HTTP 200 | 超时 | 客户端 P99 | 对应宿主 Nginx 记录 |
| --- | ---: | ---: | ---: | --- |
| 工作站 → ECS 公网 443 → 宿主 Nginx → 隔离前端 → API | 117,000／117,000／116,997 | 3 | 55.554 ms，**不掩盖 3 次失败** | 130,001 条 = 13,000 预热 + 117,000 采样 − 3 失败 + 4 身份探针；全部 200，最长 `$request_time` 31 ms |
| 工作站 → SSH 转发 → ECS 回环隔离前端 HTTP | 117,000／117,000／117,000 | 0 | 59.060 ms | 不经过宿主 443，不用于判定 TLS |
| 工作站 → SSH 转发 → ECS 回环宿主 443，保留域名／SNI／证书／TLS | 117,000／117,000／117,000 | 0 | 117.128 ms | 130,002 条 = 13,000 预热 + 117,000 采样 + 2 身份探针；全部 200 |

公网两轮的应用 `/api/errands` 计数累计 260,004，与两份公网 Nginx 已处理请求数量总和相符；Hikari `pending` 峰值 0、连接超时增量 0，宿主 CPU 中位约 36.885%。这是**采样和计数证据**，不能排除采样间隙里的瞬态，更不能用 CPU 中位数推出网卡、连接跟踪或用户线路健康。

Nginx 官方定义 `$request_time` 从**读到客户端首字节**开始到响应最后字节发送并写日志结束；access log 记录完成 HTTP 处理的请求。因此 3 次传输失败未出现在日志中，最强结论是「没有形成被宿主 Nginx 记录的完整 HTTP 请求」，并非「数据包绝未到达 ECS」。`$upstream_connect_time`、`$upstream_header_time`、`$upstream_response_time` 可用于**已经进入 Nginx 的慢请求**分段，不能解释这 3 条没有 HTTP 记录的失败。[Nginx 日志变量](https://nginx.org/en/docs/http/ngx_http_log_module.html)、[Nginx upstream 计时变量](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)。

**下一轮最低成本的定位实验**：对公网失败用客户端连接追踪记录 DNS 解析、连接复用与池等待、TCP connect、TLS handshake、首字节及错误原文；同一时钟窗口在发压机和 ECS `tcpdump`/`ss` 采样五元组、SYN/SYN-ACK/RST/重传、监听与 accept 队列；记录 Nginx TLS 握手错误和 HTTP 请求 ID。交错重复公网、SSH-443 和不同发压机，固定客户端最大连接数、超时及是否复用连接。若失败只在某一发压机出现，先查其出口和 HTTP 客户端；若两端均见 SYN 但无握手，再查 ECS 公网接入/系统队列；若已完成 TLS 而无 HTTP 日志，再查请求写入与 Nginx 连接处理。一个自定义诊断脚本虽捕获了 3 个失败时间点，但改变了实际发压节奏，**不能作为新容量结果**。

## S1：多秒延迟首先发生在业务计时之外，业务读放大仍存在

新的隔离 2,000 并发尖峰直连 ECS 回环 API，不包含公网或 Nginx；[发压器](../peergrab-bench/src/main/java/com/peergrab/bench/SpikeLoadClient.java)在开闸后、`HttpClient.send` 前记时，包含客户端连接建立、等待、请求／响应和解码。结果为 1 人成功、1,996 名额满、3 并发冲突、0 热点限流、0 系统错误，整批约 5.938 秒，客户端 P50/P95/P99/Max = 3.117/4.846/5.153/5.285 秒。**此轮与前一轮有 158–204 次热点限流的三轮 S1 不是同一到达形状**，不能仅凭 P99 变大就断言代码回退；也不能把 2,000/5.938 算成稳定 QPS。

应用 Micrometer 的 `http.server.requests` 累计 2,030 条含预热，平均约 472 ms，观测最大约 1.042 秒。Hikari 活跃峰值 5/20、`pending=0`、连接超时增量 0，GC 暂停累计增加约 0.232 秒。MySQL `Com_select` 在观测窗口增加约 16,700，常见语句的 Performance Schema digest 平均时间：`errand` 主键查询约 0.533 ms、信用分约 0.423 ms、在途数约 0.868 ms、`grab_record` 约 0.484 ms；Redis `SLOWLOG` 0 条，`EVALSHA` 均值约 41.66 µs、`ZCARD` 约 1.24 µs。digest 是窗口内均值，且包括预热／后台活动；**不能据此排除个别慢尾，也不能把 16,700 次 SELECT 精确平摊给 2,000 次抢单**。

从代码可见，[抢单用例](../peergrab-application/src/main/java/com/peergrab/application/usecase/GrabErrandUseCase.java)在 Redis 名额裁决前读取任务、信用分和在途数；满额时再查询任务、预占位及持久结果，`classifyUnavailable` 可能重读任务，候选入队又读一次信用分并查队列长度。成功者还有数据库 CAS、状态通知等提交后工作。典型失败路径可产生多次 SQL 与 Redis 往返，静态路径估算可接近 8 SQL + 4 Redis；这是**调用图估算，不是逐请求实测计数**。Tomcat 配置 200 处理线程和 500 `accept-count`，但 `accept-count` 作用于连接队列，不能视为 2,000 个请求全部立刻进入业务线程。[Tomcat HTTP Connector 参数](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)。

优先在发压器记录「开闸 → 开始 send → 连接／首字节 → 完成」，同时在宿主/容器记录 `ss -ltn` 接收队列、Tomcat 当前／忙线程与应用过滤器、鉴权、抢单用例各阶段计时，按成功／名额满／冲突／限流分桶。用 request ID 对齐客户端与服务端，先证实队列时间，再以基准 A/B 检查能否复用已读信用分、减少满额失败分支回查；保留数据库 CAS 与幂等校验。单纯提高 Tomcat 线程数可能把等待转移到数据库或 Redis，不是现阶段的结论。

## S4、S5 与 S3：明确代码可解释的等待，暂不制造新指标

[结算用例](../peergrab-application/src/main/java/com/peergrab/application/usecase/SettleErrandUseCase.java)在同一事务中处理任务状态、托管资金、信用与 outbox；[钱包仓储](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcWalletRepository.java)按账户加 `FOR UPDATE` 行锁，[信用仓储](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcCreditRepository.java)锁信用行并顺序回放近 30 天事件。共享钱包负载下，同一热点行的写事务必然要序列化，这是更强的结构性解释；但旧测试的 MySQL 行锁等待计数混入造数和核验，尚不足以量化它对约 60 TPS 的贡献。应做共享／分散钱包同口径持续负载并同步抓取 `performance_schema.data_lock_waits`、事务阶段耗时和连接池等待，再决定是否优化信用投影或账户模型；资金原子事务不可为追 TPS 任意拆开。[MySQL `data_lock_waits` 官方说明](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-data-lock-waits-table.html)。

[兜底扫描](../peergrab-worker/src/main/java/com/peergrab/worker/TimeoutScanJob.java)每次最多取 200 条，处理完成后再固定延迟 5 秒，先有 2 秒宽限期；1,000 条同刻到期自然至少跨五批，旧扫描轮约 39 秒 P99 的阶梯与配置吻合。MQ 轮关闭扫描、同刻投递 1,000 条，9 秒 P99 可能包含定时存储释放、消费者排队和业务执行；RocketMQ 官方明确提醒大量消息设置同一投递时间会增加投递延迟，**不能据此断言 Broker 单点瓶颈**。[RocketMQ 延时消息说明](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)。下一轮需在投递时间、消费开始、业务事务完成记录分段，并对扫描试验限时连续排空，同时监控对在线接口 P99 的影响。

S5 旧探针从 `errand_status_log.created_at` 算到期后的时差；该字段在状态日志 `INSERT` 时由数据库赋值，而日志行与状态更新处于事务中。它可以证明最终存在持久记录，**时间戳不是精确 commit 时间**；若事务在插入后继续执行，报告中的 9.06/39.47 秒可能低估真正提交可见时间。新的基准应在事务提交后由独立连接观察可见性，或记录明确的提交后事件，并保留数据库状态和幂等交叉校验。[S5 探针实现](../peergrab-bench/src/main/java/com/peergrab/bench/S5TimelineProbe.java)、[状态日志表](../docker/init.sql)。

S3 只做过一次冷/热消融；请求即使命中详情缓存，JWT 会话仍查 MySQL，因此「DB 详情加载为 0」并非「请求不访问 DB」。先交错重复固定到达率的开／关与冷／热轮，独立记录鉴权、Redis、重建锁和详情 SQL 时延；无证据前不应引入多级缓存或把热态 661 对 680 RPS 写成加速。
