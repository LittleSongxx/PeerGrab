# PeerGrab 校招／实习简历性能指标卡 · 2026-09-27

可从下面三条中选 2–3 条写入简历；只写自己确实参与实现和复测的部分。每条的数值均可在[专项原始证据报告](../bench/reports/peergrab-current/report-resume-metrics-20260927.md)中追溯。项目是单体后端加独立 Worker、MySQL／Redis／RocketMQ 的同机部署；本轮停生产栈后用独立数据卷发压，结束后恢复生产。

1. **列表接口与全链路压测：**对 1 万条已发布任务的首屏列表接口，构建异机 Vegeta → 公网 HTTPS → 宿主 Nginx → 隔离前端 Nginx → API 压测；固定 600 RPS 连续 3 分钟、重复 3 轮，共 32.4 万请求全部 HTTP 200，最差轮 P99 **256 ms**。
2. **热点抢单正确性：**针对单任务单名额设计 Sentinel 热点限流、并发冲突处理和数据库名额校验；在隔离栈直连 API 的 **2,000 并发同单抢单 × 3 轮**中，每轮恰好 1 人成功、0 超卖、0 系统错误，并用 SQL 交叉验证。三轮有 158／167／204 次限流；P99 为 2.77–3.14 秒。
3. **资金结算与幂等：**以本地事务、资金流水和业务唯一约束处理并发结算与重复请求；隔离栈直连 API、共享演示钱包的 **200 任务／32 线程 × 2 轮**中，持久化结算 TPS **60.8／60.3**，200／200 任务落库、系统错误与资金差额均为 0；同任务 8 次结算仅 1 次生效。

若简历空间只有两条，优先保留“全链路列表压测”和“热点抢单正确性”；面试中再展开资金结算。S2 是读接口持续负载，S1 是一次性竞争尖峰，S4 是每轮约 3.3 秒的短批次；这三类数字不能互换。S2 的第一轮主机 CPU 中位约 36.6%、Hikari 活跃峰值 9／20、等待与连接超时 0，可作为面试追问时说明当轮资源状态，避免单独写成容量指标。

面试时按“业务目标 → 请求路径和数据量 → 分母及窗口 → 正确性校验 → 失败边界”回答。列表接口 450／600 RPS 的 60 秒阶梯无错，但 750 档有 1 次传输超时，650 RPS × 180 秒有 23 次超时，所以只能说**已验证 600 RPS 下这 3 个 180 秒窗口**，不能说找到了全站最大吞吐。抢单限流是保护数据库的业务拒绝，不能写“2,000 请求全部成功”；结算 TPS 包含共享钱包竞争，不能外推真实钱包分布或长期稳态。S3 缓存实验仅证明 5,000 次详情读的数据库加载从 5,000 降到 0，**没有证明吞吐提升**；S5 到期 MQ／扫描 1,000／1,000 的数据来自此前报告，本轮没有重测。

**禁用说法：**“全站峰值／最大 600 QPS”“2,000 QPS 零超卖”“2,000 人抢单全部成功”“结算长期稳定 60 TPS”“Redis 缓存使吞吐提升”“MQ 比扫描快 4 倍”“生产线上真实用户流量 32.4 万”。对应的负载、时间、路径或对照条件不支持这些结论。也不要把本轮测试写成 Elasticsearch、Canal、Redis Cluster 或微服务架构的性能成绩；项目未采用这些部署。
