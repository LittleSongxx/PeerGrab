# 生产成熟度深挖与技术方案取舍（2026-09-27）

> 本文保留整改前的源码审查快照，A/B 条目是当时的发现，不应再逐条当作现行缺陷。已实施的修复和仍需容量证据的取舍见[校招实习项目取舍与面试讲述方案](校招实习项目取舍与面试讲述方案-20260927.md)及当前代码；线上部署还须按[迁移步骤](../docker/ECS_DEPLOY.md)执行。

范围：当前工作区源码、部署/初始化脚本、CI、压测客户端，以及官方技术资料。工作区包含上一轮尚未发布的整改，不能将这里的代码状态当作线上状态。本轮没有修改业务代码、部署服务或重新进行大规模压测；执行了只读配置复现和确定性规则计算。

结论：保留模块化单体、单 MySQL 本地事务与 outbox 是合理主线。当前优先级最高的工作是修复跨层契约、时间裁决和故障恢复，而非增加 ES、Canal、微服务、Seata 或分片。上一轮 199 项通过证明了已覆盖路径，未覆盖真实 RocketMQ 类型契约、更新后的压测鉴权以及全部 CI 发布配置，不能作为“生产级已经完成”的证明。

**判断标准。** 将事项分为：A＝不依赖规模也应修复的缺陷；B＝真实用户/持续运营前必须明确的承诺；C＝由负载或组织复杂度触发的可选能力。P1 表示应在本轮代码发布前处理，不代表已在线上发生事故；P2 表示需要计划治理或产品规则确认。以下“已证实”是源码或只读复现确认，故障影响若未演练会明确注明。

**A1／P1：资金 outbox 的发送类型与 Topic 初始化契约不一致。**

- 当前 [FundEventOutboxJob.java:48](../peergrab-worker/src/main/java/com/peergrab/worker/FundEventOutboxJob.java) 通过普通 `producer.send(message)` 投递。
- [init-mq-container.sh:34](../docker/init-mq-container.sh) 与 [init-mq.sh:45](../docker/init-mq.sh) 仍将 `errand-fund-event` 声明为 `TRANSACTION`。
- 项目使用的 RocketMQ 5.3.1 Proxy 源码默认开启类型检查，并拒绝非 MIXED Topic 的类型不匹配消息：[ProxyConfig](https://github.com/apache/rocketmq/blob/rocketmq-all-5.3.1/proxy/src/main/java/org/apache/rocketmq/proxy/config/ProxyConfig.java)、[类型校验器](https://github.com/apache/rocketmq/blob/rocketmq-all-5.3.1/proxy/src/main/java/org/apache/rocketmq/proxy/processor/validator/DefaultTopicMessageTypeValidator.java)。通用文档对默认开关的叙述不完全一致，此处以锁定版本源码为依据。

按仓库默认 5.3.1 Proxy 配置，资金可在 MySQL 提交，事件投递则被拒绝并留在 PENDING；这不是资金被重复扣划，而是通知链路无法排空。当前 mock Producer 测试和“无 Broker 仍能提交”测试无法发现这一契约错误。应统一普通事件 Topic 及其生产、消费配置，验证现有 Topic 属性、历史消息与位点后制定迁移，不直接删除旧 Topic。验收需有真实 Broker 的“资金提交→投递→持久通知→积压清零”链路。

**A2／P1：压测客户端与新 JWT 会话契约不兼容，CI 示例也未同步。**

[BenchJwtTokens.java:35](../peergrab-bench/src/main/java/com/peergrab/bench/BenchJwtTokens.java) 自签 token 只有 sub/jti/iat/exp；[JwtAuthAdapter.java:122](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/auth/JwtAuthAdapter.java) 要求 sid 与 MySQL 会话。因此依赖该生成器的 S1/S4 HTTP 客户端会被拒绝，不能沿用旧报告推导当前版本容量。

只读复现了 CI 中生产 Compose 验证步骤：使用 `.env.prod.example` 和 CI 提供的两项 MySQL 口令执行 `config --quiet`，因缺少 `PEERGRAB_AUTH_JWT_SECRET` 退出 1。[CI:50](../../.github/workflows/ci.yml) 未注入该值，样例文件也未提供。测试环境可配置专用非生产密钥；压测凭证则通过真实登录或明确隔离的 DB session fixture 创建，不能放松生产校验。

CI 后端目前仅 `mvn test`，没有开启 `peergrab.it` 或创建中间件。应把隔离 MySQL/Redis 集成测试、真实 RocketMQ 契约测试、旧库升级及关键 HTTP 冒烟加入持续门禁，并检查预期 IT 未被跳过。现有 Compose 已可复用，无须仅为形式更换测试框架。

**A3／P1：ID 租约失败后的拒绝发号，尚未与健康检查和恢复策略接通。**

[JdbcSnowflakeNodeLease.java:104](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/config/JdbcSnowflakeNodeLease.java) 对任意续租数据库异常永久 revoke，后续 renew 直接返回；该 JDBC 使用业务同一个连接池，因此连接池饥饿也可能触发。API readiness 只核验数据库，Worker 心跳只证明线程池能调度，均未检测发号能力。

故障时序为“瞬时 SQL/连接超时→永久停止发号→数据库恢复→readiness 恢复 UP→写请求仍失败”。拒绝不安全发号应保留；需要增加发号可用性健康项、摘流和告警，并选择受控退出重启或取得安全新节点后的恢复。不能直接解除旧生成器的 revoke。美团 [Leaf 的官方设计](https://tech.meituan.com/2017/04/21/mt-leaf.html)可借鉴依赖隔离、时间异常处理和号段缓冲思想；当前不必增加独立发号服务。

**A4／P1：候选递补成功路径漏掉缓存失效。**

[TimeoutTransferUseCase.java:165](../peergrab-application/src/main/java/com/peergrab/application/usecase/TimeoutTransferUseCase.java) 成功流转后只确认候选租约、发送下一轮消息并返回；回退路径才执行缓存删除。新候选 B 已成为 MySQL 持有人，缓存仍可返回 A 与旧 round。详情逻辑有效期约 4–6 分钟，确认窗口是 5 分钟，可能让新候选在整个确认窗口内看到错误动作。

应把所有任务状态变更的提交后缓存失效纳入统一事件/编排；若需要提醒新候选，要登记可补读的持久通知。仅增加 Caffeine、多副本 Redis 或全量预热会扩大此处旧数据的传播面。

**A5／P1（真实交易前）：系统自动操作缺少数据库到期裁决。**

[AutoSettleConsumer.java:74](../peergrab-worker/src/main/java/com/peergrab/worker/AutoSettleConsumer.java) 收消息就以 SYSTEM_OPERATOR 结算；[SettleErrandUseCase.java:90](../peergrab-application/src/main/java/com/peergrab/application/usecase/SettleErrandUseCase.java) 和 [casSettle:206](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcErrandRepository.java) 只检查状态/版本，没有 deadline。确认超时处理也只有状态和轮次检查。应用用 `Instant.now()` 生成投递时间，数据库状态时间用 `NOW(3)`；时钟偏差、期限规则改变或错误的早到消息均可能使系统提前执行。

应持久化 confirm_deadline/auto_settle_deadline，将 MQ 当作唤醒信号；系统路径的同一 CAS 还要满足数据库时间已经到期。人工确认结算保留人工语义。已有扫描可以补漏执行，不能补偿提前打款。

版本核查须特别谨慎：[通用定时消息文档](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)给出默认 24 小时限制，并描述越界的立即投递行为；项目对应的 [5.3.1 Proxy 代码](https://github.com/apache/rocketmq/blob/rocketmq-all-5.3.1/proxy/src/main/java/org/apache/rocketmq/proxy/grpc/v2/producer/SendMessageActivity.java)则会拒绝超出默认 1 天范围的请求。不能断言本项目“配置超过 24 小时就一定立即结算”。无论哪一种行为，业务到期条件都应由数据库自行验证。

**A6／P2：信用实时计算与重建公式不同，且一部分处罚可以丢失。**

[JdbcCreditRepository.java:65](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcCreditRepository.java) 每次对已裁剪分数加减，再裁剪至 0–100；校准则计算 `clip(60+SUM(30天事件))`。确定性例子：30 次 +2 后为 100，再 -5 后为 95；没有新增或到期事件，重建却变为 100。版本 CAS 解决并发覆盖，不解决公式不等价。

先确定业务语义。如果选窗口贡献求和后裁剪，就保存未裁剪贡献或一致地重算；若选按事件顺序逐次裁剪，则重放算法、顺序和窗口基准也须一致。另有超时回退扣分在业务事务提交后尽力写入，宕机后无法从缺失事件重建。信用已经参与抢单资格，建议把处罚事件与回退同事务登记，不能仅以“展示数据”定位。

**A7／P2：消息重复已做业务幂等，但投递状态还不完全单调。**

[JdbcLocalMessageRepository.java:39](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcLocalMessageRepository.java) 没有待发领取协议，markRetry 也没有 PENDING 状态条件。两个 Worker 中一个标 SENT 后，另一个失败可将它改回 PENDING。资金 outbox 的更新有 PENDING 条件，但领取仍会重复。

成熟增量是 `PENDING→INFLIGHT(lease_token,lease_until)→SENT`，确认/失败更新须匹配领取 token，过期租约可重领；外部发送完成而本地确认前退出仍会重复，因此消费者业务唯一键不能删除。另需 DLQ/DEAD 的告警、可审计重放和保留期限。[RocketMQ 官方最佳实践](https://rocketmq.apache.org/docs/bestPractice/01bestpractice/)明确要求业务幂等；[消费重试文档](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)也区分重试与死信。这个问题不需要引入分布式事务框架。

**A8／P2：缓存最终一致是合理取舍，但承诺与实现需要一致。**

固定 500ms 双删不能阻止“旧数据库读取暂停超过双删间隔后才回填”。抽样 100 条/5 分钟也不是全量实时纠偏。抢单/资金裁决仍读数据库，所以这主要是展示和可用动作的新鲜度风险。应先确定可接受的陈旧时长；严格要求写后立即可见的场景可回传已提交状态、短暂绕过缓存，或增加能阻止旧回填的版本水位。只比较当前缓存版本不能防止删除后的旧写重新创建，还需定义删除/版本栅栏与过期语义。

当前单 Redis + 单片 + Bloom 默认关闭有合理性。增加本地一级缓存以前，要证明 Redis RTT/吞吐是瓶颈。[JetCache 官方实现](https://github.com/alibaba/jetcache)提供 BOTH、syncLocal、自动刷新与加载保护，可作为减少自研代码的候选；这些能力仍需验证通知丢失和本地 TTL 下的一致性边界。

**B1／P2：认证链路可用性提升了，但引入了新的资源与会话生命周期成本。**

JWT 当前每请求查 MySQL session/jti，实际是有状态鉴权；这换来了 Redis 故障下鉴权与即时撤销能力，但把读取压力转移到核心数据库。全会话撤销与 jti 单 token 黑名单的职责应再梳理，避免无效的双重状态。

过期会话以每登录 1/256 概率清理 100 条，期望最多清理 0.390625 条/登录，而每次登录创建一条会话。稳态持续流量下无法回收所有过期会话；应采用独立分批清理、保留窗口、积压和耗时指标。[JwtAuthAdapter.java:230](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/auth/JwtAuthAdapter.java)。WebSocket 只握手验 token，既有连接不随登出/过期失效；真实用户前需绑定 sessionId/到期时间，并实现关闭事件及周期复核。

**B2／P2：热点限流不等于整体过载保护。**

当前 Sentinel Entry 在 tryPass 内立即退出，实际业务耗时和并发不在其生命周期内；规则仅限制单 JVM、单任务 QPS。不同任务同时涌入、Redis 黑洞超时、数据库锁等待仍可耗尽线程和连接池。

先落实 API/下游的总时间预算、整体入口并发上限、数据库回源限额及低优先级任务隔离；采用 [Sentinel 系统保护](https://sentinelguard.io/zh-cn/docs/system-adaptive-protection.html)或熔断时需包住真实调用。多实例确需统一总量才引入 [Sentinel 集群流控](https://sentinelguard.io/zh-cn/docs/cluster-flow-control.html)，不必先部署注册中心和微服务网关。

**B3／P2：数据生命周期与后台批处理需要预算。**

候选 ZSET 无人数上限；校区排行榜保留全量成员；SENT outbox、通知和历史表没有统一归档/清理策略。`CreditRankingRebuildJob` 每分钟全量投影，缓存校验 `ORDER BY RAND()`，数据增长与多 Worker 会放大周期负载。应为候选队列明确最大候补人数/排队有效期，为榜单定义 TopN 与历史窗口，按业务保留期限分页清理或增量重建。资金账本需独立审计保留策略，不能跟临时消息一起 TTL。

阿里云[大 Key/热 Key 官方指引](https://help.aliyun.com/zh/redis/user-guide/identify-and-handle-large-keys-and-hotkeys)建议按成员数、内存和访问频率识别再治理；Redis Cluster 按 Key 分布，不能自动拆散单个大 Key。当前详情 JSON 小，不值得先压缩；候选队列与排行的上限/指标更实用。

**B4／P2：监控、备份和迁移已有入口，尚缺完整执行证据。**

Prometheus 指标已暴露，但仓库未提供抓取、告警规则和通知路由；Worker 心跳没有覆盖每种业务任务的最后成功时间。采样异常时保留旧指标，可能把“监控失败”显示成“仍为零积压”。增加指标采样时间、新鲜度、连续失败数、任务延迟及外部合成拨测；按 requestId/errandId/bizNo 关联 API、outbox 和消费日志。跨进程定位需求增长时可接入 [SkyWalking 关联上下文](https://skywalking.apache.org/docs/skywalking-java/v9.6.0/en/setup/service-agent/java-agent/application-toolkit-trace-correlation-context/)，当前先做好业务关联标识即可。

已有逻辑备份脚本和恢复说明，但缺自动调度、异地存储失败告警、日志连续性/PITR 与实际恢复耗时记录。参考[阿里云 RDS 备份指引](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/backup-guide)的全量+日志恢复能力，根据本项目可接受的数据损失与停服时间选择方案，而非照搬所有云产品。

当前迁移 SQL 依赖手动顺序和 IF NOT EXISTS。多次发布后应采用版本化、可校验的迁移；可借鉴 [Flyway schema history](https://documentation.red-gate.com/fd/flyway-schema-history-table-273973417.html)记录版本、校验和及执行结果，并分别测试新库安装、旧库升级和重复执行。涉及 Topic、密钥、应用镜像的迁移也应纳入同一发布清单。

**B5：真实交易的准入条件应独立于演示评分。**

当前明确是公开四身份与虚拟资金。缺少实名/角色权限、支付接入、提现、交付证据、申诉审计并不自动构成演示缺陷；若转为真实运营则必须补齐。账务还需订单级费率/期限策略快照、整数或精确十进制计费、期初凭证、逐业务借贷和账户连续性对账、外部支付账单核对。当前 `SettleErrandUseCase` 在结算时读取运行配置且用 double 计算佣金；成功审计及信用展示查询又发生在提交后，可能出现钱已提交而响应报错/审计遗漏。应区分成功财务事实、失败尝试审计与可丢展示通知，逐一明确事务边界。

**C 类技术取舍矩阵。** 下列是针对本项目的判断，不是厂商市场份额排名。

| 候选方案 | 当前判断 | 引入触发条件与先做的最小工作 |
| --- | --- | --- |
| Spring Cloud / Dubbo / Nacos 微服务体系 | 暂缓 | 多团队独立发布、明显不同的扩缩容和故障隔离需求出现后再拆。当前单库资金一致性与模块边界应保留。 |
| ES 搜索 | 暂缓 | 全文检索、模糊召回、相关性排序、复杂多维检索形成明确需求且 MySQL 查询方案不足时。首屏分页 QPS 本身不能证明需要 ES。 |
| Canal / CDC | 暂缓 | 多个异构下游、跨应用数据库写入或搜索/数仓增量同步需求出现时；需要快照衔接、binlog 位点、DDL 兼容、重放与延迟监控。[Canal 官方原理](https://github.com/alibaba/canal/wiki/Introduction)及[ROW binlog 配置](https://github.com/alibaba/canal/wiki/AdminGuide)。CDC 是数据变化捕获，不代替资金本地事务。 |
| JetCache/Caffeine 二级缓存 | 条件性 PoC | 热读的 Redis RTT/带宽占比已测得，允许短暂陈旧，能负担各 JVM 容量与失效复杂度。先采样热门键和本地命中收益；不把余额/抢单真值放入 L1。 |
| 缓存预热 | 只做有界热点预热 | 有可预测活动或重启后冷态 SLO 问题时，按 TopN、限速、单执行者预热，失败不阻断启动。没有证据时不全库扫描装入缓存。 |
| Redis Sentinel/托管 HA | 有可用性承诺时优先于 Cluster | 先解决主节点失效与恢复目标；Cluster 仅在容量/吞吐证据要求分片时采用。当前 Redisson 只读 host/port，不支持所需密码/TLS/拓扑，外接服务前先统一双客户端配置。 |
| XXL-JOB | 批处理运维需求增长再引入 | 对账、校准、重建需要控制台、分片、告警、人工重跑时有价值；不替代订单 deadline 和业务幂等。[官方能力](https://github.com/xuxueli/xxl-job/blob/master/README.md)。 |
| Seata | 当前不需要 | 本地单库已能原子提交。AT 需要 undo log/全局锁并有隔离语义约束，引入只会增成本；确实拆成多个写数据库后才重新设计事务。[Seata AT 官方说明](https://seata.apache.org/zh-cn/docs/dev/mode/at-mode)。 |
| ShardingSphere/资金分库 | 暂缓 | 单库在索引、归档、资源隔离、热点账户优化后仍达到物理瓶颈，且路由键/账务共片方案明确。共享演示钱包的 S4 结果不能直接代表真实分散用户。 |

**建议实施顺序与验收。**

1. 发布前先修 A1–A5，并恢复 CI 与压测凭证契约；真实 Broker、正常递补缓存刷新、早到自动消息和租约失效恢复都应有可复现验收。
2. 统一信用规则、投递领取状态机、提交后错误隔离和用户会话生命周期。多 Worker/进程强杀/Redis 慢超时/DB 池饥饿要测恢复后的业务事实，不只测最终返回码。
3. 建立版本化迁移、备份恢复演练、指标新鲜度与真正告警，再按已约定的可用性目标考虑外部 HA 数据库和 Redis。
4. 以新鉴权与缓存配置重跑 S1–S5；先做缓存开关/单片多片、共享/分散账户分布、Worker 积压排空的对照。达到明确瓶颈后再从 C 类矩阵引入一个变量。

本轮实际验证：按 CI 配置执行生产 Compose 校验，复现 JWT secret 缺失；按当前公式确定性计算信用分 95/100 不一致和会话清理上限 100/256；联网核对 RocketMQ 5.3.1 版本源码。其余故障时序来自源码审查，未声称已在生产发生，也未以旧压测数字承诺整改后容量。
