# PeerGrab 架构与技术选型评估

> 范围：2026-09-25 修复前的工作区源码和本地 Docker 演示栈。下文“当前”均指审查时的基线，列出的缺口并非全部仍存在；代码修复与工具冒烟见[性能压测与架构决策方案](性能压测与架构决策方案.md)及[当前版本冒烟记录](../bench/reports/smoke-20260925-current.md)。历史数字不代表当前版本容量。

## 评估目标

当前系统是**单名额校园跑腿交易的工程演示**：发布并托管悬赏，竞争抢单、限时确认、取送、结算或退款，另有争议仲裁、信用分、通知和对账。任务只包含类型、标题、悬赏及单人状态；没有地点、时限、联系人、详细说明和交付凭证（[任务聚合](../peergrab-domain/src/main/java/com/peergrab/domain/errand/model/Errand.java)、[任务表](../docker/init.sql)）。用户是四个固定演示身份，钱包靠种子数据初始化。正式校园交易平台所需的账户、充值提现、身份和交付证据并未实现。

因此“最优”的硬约束先是**零超卖、零重复结算、资金与托管闭环、故障后可恢复**；再比较目标流量下的 P99、稳定吞吐和资源成本。没有真实需求量与 SLO 时，不能给出唯一最优架构。

## 各模块设计

| 模块 | 功能与技术 | 判断 |
|---|---|---|
| `peergrab-shared` / `peergrab-domain` | Java 21，整数分金额、状态机、聚合和端口；领域层无框架依赖 | 分层清楚，适合当前业务。`CLOSED` 等未落地分支可收敛。 |
| `peergrab-application` | 发布、抢单、流转、资金、仲裁的事务编排 | 单库本地事务是当前资金正确性的优势；同步路径混有 Redis/MQ 外部 IO，增加尾延迟。 |
| `peergrab-infrastructure` | MySQL JdbcTemplate/CAS、Redis Lua/缓存、RocketMQ、Sentinel、ShardingSphere 规则 | 精确 SQL 易验证；Redis/MQ/多层缓存的复杂度应由 A/B 收益证明。ShardingSphere 尚未激活。 |
| `peergrab-presentation` | REST、演示鉴权、WebSocket、`availableActions` | 前端只展示后端计算的动作，方向合理；演示身份不能作为真实用户认证。 |
| `peergrab-worker` | 延迟消费、兜底扫描、消息重试、信用校准、缓存校验、对账 | 在线/后台分进程合理；单线程调度与批量扫描容量需测。 |
| `peergrab-bench` / `bench` | 尖峰/阶梯/缓存客户端、SQL 校验与历史报告 | 能支持部分正确性检验；当前工具、数据与文档口径不一致，不能直接推出容量最优。 |
| React 前端 | 七页闭环、状态驱动操作、WebSocket 加轮询 | 教学演示足够；真实平台的信息采集与资金入口不足。 |

## 核心链路判断

### 发布与资金

[发布用例](../peergrab-application/src/main/java/com/peergrab/application/usecase/PublishErrandUseCase.java)在同一 MySQL 事务中扣用户户、加托管户、写借贷流水/托管单并发布任务，金额以整数分保存；[账户仓储](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcWalletRepository.java)使用条件 UPDATE。这比现在启用跨库分片更适合保证原子性。

当前所有任务共用同一 ESCROW 账户行。发布按 USER→ESCROW 更新，结算与退款按 ESCROW→USER 更新：不同任务也被该行锁串行化，并有混合流量反向锁序死锁风险。扩大 Hikari 池不能消除同一行的互斥。发布事务内还调用 Redis 名额初始化和 Bloom 登记，慢外部调用会延长持锁时间。

`wallet_ledger.balance_after` 由更新前读到的 Java 对象计算。两个事务若先读取同一余额、随后串行 UPDATE，第二笔余额变动本身正确，但单条流水的“变动后余额”可能仍是旧快照推导值；结算与退款也同型。现有对账只看借贷总额、系统户余额和托管闭环，没有检查每条 `balance_after`。这是**代码推导风险**，本次在演示库的只读小样本查询没有发现已存在的系统户错行；不能据此排除高并发问题。建议统一账户锁序、增加死锁重试，并在行锁下取得真实结后余额；流水加入账户版本/严格序号，以便逐条审计。

### 抢单与候选队列

数据库 CAS 和唯一索引作为最终裁决合理，Redis Lua 适合经证明确有热门抢单峰值的场景（[Redis 原子脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)）。但当前每个通过单实例限流的请求在 Lua 之前仍读任务、信用和在途数；在途统计没有以 `grabber_id` 开头的适配索引。限流也是每实例阈值，并非集群统一预算。应先测 DB CAS 单独方案与现有 Lua+DB 方案的成功、名额满和限流路径成本。

Redis slot 只在发布时创建一次，TTL 为七天，缺键直接返回“不可抢”；任务没有七天到期约束。Redis 容器未挂数据卷，重建或 TTL 到期后，MySQL 中仍开放的任务可能无法抢。必须有按 DB 状态安全重建名额或 DB CAS 降级路径。`requestId` 的 Redis 幂等键没有绑定 runner，重复键会直接向调用者回复抢中成功而不核实持久化结果；应以 `(errandId, runnerId, requestId)` 和数据库抢单记录作为幂等最终答案。候选队列的 ZRANGE→ZREM 是两条 Redis 命令，并发消费者可选到同一候选；可以 A/B 测原子 [ZPOPMIN](https://redis.io/docs/latest/commands/zpopmin/)。

### 异步、缓存与后台任务

本地消息表、MQ 和 DB 扫描兜底体现了正确的重复消费防护方向，但 24 小时自动结算消息目前直到到期才由 worker 发出，数据库扫描可能先处理。RocketMQ 5 默认定时消息窗口上限为 24 小时，过去时间会立即投递，集中同一时间投递也可能延迟（[官方文档](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)）。需要量测 MQ 实际贡献，再选提前分段调度、可靠 DB 调度或其他方案。

Spring Boot 3.5 普通调度池默认一个线程（[官方文档](https://docs.spring.io/spring-boot/3.5/reference/features/task-execution-and-scheduling.html)）；worker 未指定池大小，超时/结算扫描、重试、校准和对账互相排队。两类兜底扫描各最多 200 条/5 秒，1 万条同时到期只按轮次计算下界就约 250 秒，还没计 SQL、消息或失败重试。应测自然到期 P99、积压清空时间，以及前 200 条失败造成的后续饥饿。

详情缓存含 Cache Aside、逻辑过期、Bloom、4 份热键副本、Redisson 锁和延迟双删。当前只用单 Redis 实例，4 份副本不会把 CPU 分到不同节点，却增加写放大；冷 miss 和删缓存后的并发回源不受现有重建锁保护。Bloom 消失后如果先发布新任务，会创建只含新 ID 的过滤器，旧任务详情可能被误判不存在。信用分每日校准修 MySQL，但没有同步重建排行榜 ZSET。缓存与投影都需要恢复测试，且以关缓存/1 副本/4 副本同条件对照决定复杂度。

### 数据库分片

[规则工厂](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/sharding/PeerGrabShardingRuleFactory.java)只有实验代码，运行配置仍是单 MySQL。任务按校区、账户按用户分片的规则若直接启用，会使发布和结算跨片，失去当前本地事务原子性；很多 `findById(id)` 查询也不带分片键。应先在单库修索引、热点行和恢复路径；只有容量证据证明单库达到物理上限时，再重新设计资金共片或跨片一致性。

## 暂定最优方向与验证顺序

1. **P0 正确性/可恢复性**：修流水结后余额、统一账户锁序与重试、Redis slot 重建、`requestId` 幂等最终答案、Bloom/排行榜恢复。没有这些，性能更高不代表设计更好。
2. **可观测性**：给 REST/用例阶段、Hikari 等待、Redis RTT、MQ backlog、Worker 到期误差、MySQL 行锁和死锁建立同一轮次指标；当前无 Actuator/Micrometer 运行配置。Spring Boot 可自动提供 `http.server.requests` 等指标（[官方文档](https://docs.spring.io/spring-boot/reference/actuator/metrics.html)）。
3. **基线**：单库模块化单体、DB CAS/唯一索引、app/worker 分进程；固定版本、数据规模、资源配额和 SLO，先测列表、详情、热点抢单、分散抢单、完整资金链与自然超时。
4. **每轮一个变量**：DB CAS vs Lua+DB；详情无缓存 vs 1/4 副本；单托管户 vs 合理分桶；当前 MQ vs 同事务 outbox/DB 调度；Hikari/Tomcat/worker 池分别调参。记录吞吐、P95/P99、业务码、系统错误、锁等待、内存和对账。
5. **选择规则**：正确性不变式全部通过，在目标流量和故障下满足 P99/错误率/恢复 SLO，资源有余量且成本最低的配置进入推荐方案。未证明收益的组件应避免成为新的强依赖。

历史 P7 的 6455 QPS/P99 151ms 是旧版同机 60 秒的任务广场 GET 列表，S4 的约 191 TPS 是 MQ 关闭后同 JVM 用例调用；它们不能证明当前抢单或完整交易容量（[历史报告](../bench/reports/report-P6-P7-20260822-complete.md)、[旧资金报告](../bench/reports/report-P3-20260819-020300.md)）。连接池大小也应通过真实负载比较，Hikari 官方将常见公式仅作为起点并要求针对部署实测（[官方说明](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)）。
