# PeerGrab 校招／实习简历性能指标卡：JMeter ECS 轮 · 2026-09-28

仅引用当前业务镜像 `5ace500` 的[JMeter ECS 实测报告](../bench/reports/peergrab-current/report-ecs-jmeter-20260928.md)：8 vCPU、100 Mbps 单 ECS，维护窗口停生产、逐场景独立数据卷、JMeter 5.6.3 CLI。它是指定路径和有限时间窗的个人项目实验，不是全站容量或真实用户 SLA；旧 Vegeta／Java 结果保留原工具名，**不能跨工具计算优化百分比**。

简历可优先选自己能解释原始 JTL、SQL 和负载模型的两项：

1. **公网广场读取：**用异机 JMeter 经 HTTPS 与双层 Nginx 压测 1 万条任务的游标首屏；固定用户池配合吞吐定时器，在 **500 目标 RPS × 180 秒 × 3 轮**中实际开始 **269,608 次请求，全部通过 HTTP 与业务断言**，最差轮 P99 **255 ms**。目标 600 RPS 的 180 秒长档第二轮有 **1 次连接超时**，第三轮按门禁停止，故不写“最大／稳定 600 QPS”或“零错误 600 RPS 三轮”。
2. **并发抢单正确性：**JMeter 以不同用户令牌争抢单任务单名额；**2,000 次尝试**中恰好 1 人成功、0 超卖、0 系统错误，数据库名额和抢单记录复核通过。请求实际开始时间横跨 **2.228 秒**、P99 **8.735 秒**，同机发压时宿主 CPU 峰值约 99.5%；因此不写“2,000 个请求同一瞬间到达”或“2,000 QPS”。
3. **热点资金结算：**完成真实 HTTP 履约准备后，用 32 线程结算 200 个不同任务，200/200 持久成功；同任务 8 次结算仅 1 次生效、资金不变量通过。短批次约 **34.72 持久化 TPS**、P99 **1.081 秒**；窗口累计行锁等待 205 次／68.4 秒，含准备阶段，不能说是长期稳定 TPS 或单请求锁耗时。

缓存可作为追问展开：关／开分别在独立栈做三批各 5,000 次详情读，MySQL `Com_select` 窗口增量 **30,460 → 15,526**，约少 49%；但开缓存的首批冷态 P99 **479 ms** 高于关缓存的 **246 ms**，不能声称吞吐已提升。新栈的 500 发布＋4,500 读取全部成功、抽样差异 0，但不证明所有并发时刻强一致。Redis 暂停时 JMeter 详情读仍成功，P95 升至 2.109 秒；Broker 暂停下的已提交结算客户端超时问题尚未修复。

面试里先说清 **工具回答什么问题**：S2 的 128 用户池＋Constant Throughput Timer 只尝试目标 RPS，服务变慢时实际发出率可能下降；S1 的 Synchronizing Timer 释放线程也不等于请求同时抵达。再给出实际样本数、错误分母、P99、数据库真值和失败档。JMeter 静态 HTML 报告属于压测结果展示，不能称为生产 Grafana 看板或链路追踪。
