# 校招／实习面试证据卡（现行实现）

这三张卡只讲已经落地、能在代码和测试里定位的行为。项目是 API 与 Worker 分进程的模块化单体，任务和资金共用一个 MySQL 事实源；单名额、虚拟资金、个人部署是明确边界。压测数字须连同环境、时长和请求分布展示，不能当作线上容量。

## 1. 抢单与资金：最终裁决在 MySQL

业务约束是同一任务只允许一个跑腿抢中，余额不能扣成负数，一笔转账借贷额相等。Redis Lua 提前降低竞争性写入；[GrabTransactionalStep](../peergrab-application/src/main/java/com/peergrab/application/usecase/GrabTransactionalStep.java)把跑腿额度锁、任务状态/版本 CAS、抢单记录及状态日志放入同一事务，唯一键再兜底。Redis 预占成功而数据库失败时，事务外释放预占；Redis 不是名额的最终事实。

[WalletPosting](../peergrab-application/src/main/java/com/peergrab/application/usecase/WalletPosting.java)用整数分检查借贷守恒，按账户 ID 固定顺序 `SELECT FOR UPDATE`，再条件更新余额并写流水。[结算用例](../peergrab-application/src/main/java/com/peergrab/application/usecase/SettleErrandUseCase.java)将任务、托管单、资金流水、信用事件和 outbox 放入一个本地事务。这里能展开 Spring 代理自调用、RC 当前读、行锁顺序、死锁重试、唯一键与幂等业务号。证据是 [GrabConcurrencyIT](../peergrab-bootstrap/src/test/java/com/peergrab/it/GrabConcurrencyIT.java)、[WalletLedgerConcurrencyIT](../peergrab-bootstrap/src/test/java/com/peergrab/it/WalletLedgerConcurrencyIT.java)、[SettlementIT](../peergrab-bootstrap/src/test/java/com/peergrab/it/SettlementIT.java)。

边界：业务只支持 `slotTotal=1`。若未来多个名额、多个资金库或外部支付成为真实需求，需重新定义库存守恒和对账，不能把当前本地事务口头升级为跨服务强一致。

## 2. Outbox 与超时：至少一次，消费者幂等

业务事务先写事件，Worker 再发送。[资金 outbox](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcFundEventOutboxRepository.java)和[延迟本地消息](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcLocalMessageRepository.java)用领取 token 与过期租约协调多个 Worker；成功确认必须匹配 token。发送成功、确认前退出仍会重复，所以 `biz_no`/`msg_key`、状态 CAS 和通知唯一键承担业务幂等。资金事件使用 `NORMAL` Topic，不能把普通消息投到旧 `TRANSACTION` Topic；[契约脚本](../docker/verify-fund-topic-contract.sh)验证真实 Broker 的类型、发送与读回。

RocketMQ 的定时消息只负责唤醒。[确认超时](../peergrab-application/src/main/java/com/peergrab/application/usecase/TimeoutTransferUseCase.java)和[自动结算](../peergrab-application/src/main/java/com/peergrab/application/usecase/SettleErrandUseCase.java)在数据库 CAS 中再次验证持久截止时间；Worker 扫描在 MQ 不可用或消息丢失时补偿。早到、晚到、重复到达都不会让尚未到期的任务提前改变。证据是 [TimeoutTransferIT](../peergrab-bootstrap/src/test/java/com/peergrab/it/TimeoutTransferIT.java)、[FundOutboxWithoutBrokerIT](../peergrab-bootstrap/src/test/java/com/peergrab/it/FundOutboxWithoutBrokerIT.java)和真实 Broker 契约检查。

边界：这不是端到端 exactly-once；MQ 长期关闭会积累待发送记录。账务事实仍在 MySQL，恢复时先看 PENDING/DEAD、重试延迟和消费者幂等结果，再评估排空速度。投递表的保留/归档期限与真实业务审计期限应分开决定。

## 3. 查询与缓存：先测 SQL，再限定陈旧窗口

广场和流水查询依赖联合索引与稳定排序；[查询适配器](../peergrab-infrastructure/src/main/java/com/peergrab/infrastructure/persistence/JdbcErrandQueryAdapter.java)和[游标分页测试](../peergrab-bootstrap/src/test/java/com/peergrab/it/CursorPaginationIT.java)可解释同时间戳下 ID 如何破平局。[深分页对照 SQL](../bench/scripts/compare_deep_page.sql)用 `EXPLAIN ANALYZE` 观察实际扫描行数与耗时，不能只拿优化器估价或本地毫秒数概括线上 P99。

任务详情默认单 Redis key：Cache Aside、TTL 抖动、短空值、互斥重建；[统一失效入口](../peergrab-application/src/main/java/com/peergrab/application/usecase/CacheEvictSupport.java)在事务提交后删除并安排一次延迟双删。对照 [CacheStaleReaderWindowIT](../peergrab-bootstrap/src/test/java/com/peergrab/it/CacheStaleReaderWindowIT.java) 可说明慢读者在双删之后才回填旧值的残余窗口；展示缓存允许有界陈旧，抢单与资金裁决仍读数据库。多片、Bloom 只是显式容量实验，不能把单 Redis 上的多 key 当作集群高可用。

升级门槛：先测 Redis 热 key 访问频率/RTT、详情 JSON 字节数、候选 ZSET 和信用榜单成员数；如果读延迟或内存成为瓶颈，再选择热点副本、本地缓存同步方案或数据结构限额。ES/Canal 需要全文检索或异构同步需求，不能为了面试关键词引入。

本轮隔离 MySQL/Redis 运行的后端测试为 **214 项，0 失败、0 跳过**；前端 `npm run build`、后端 `mvn -DskipTests package` 和本机 Compose 配置校验通过。真实 RocketMQ 契约另行验证了 Topic 类型和消息发送/读回；完整业务链路压测、真实流量容量和生产部署仍需按各自环境单独验收。
